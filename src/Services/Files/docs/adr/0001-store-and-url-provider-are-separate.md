# 字节存储的能力拆成两个接口

`IFileStore` 只有三个方法：写、读、删。**签发访问链接不在其中**——
它在另一个接口 `IFileUrlProvider` 上，只有对象存储实现它。

## 为什么

参照仓库的 `IFileStorage` 有 14 个成员，而**没有任何一个实现支持全部成员**：
`AliyunFileStorage.GetAbsolutePath` 抛 `NotImplementedException`，
偏偏视频上传路径会调到它，于是那条路一上传就崩。

一个给不出本地路径的存储（因为它根本没有本地路径）不应该被要求实现 `GetAbsolutePath`。
**做不到的能力不给接口，就没有"声明了却抛异常"的中间状态。**

## Considered Options

- **一个大接口**：调用方少注入一个依赖。代价是每个实现都要为用不到的能力抛异常或空实现，
  而调用方**无从知道**手里这个实例哪些方法能用——只能靠运行时崩一次来发现。
- **拆成两个**：本地磁盘存储只实现 `IFileStore`；对象存储两个都实现。
  需要 URL 的调用方显式依赖 `IFileUrlProvider`——**依赖关系本身就是能力声明**。

## Consequences

- 这道缝上的两个适配器是**具名的**：本地磁盘与对象存储。按深模块的判据
  （一个适配器只是假设的缝，两个才是真的缝），这是一道真缝。
  已用两个语义刻意不同的适配器跑同一组契约断言验证过
  （`tests/Contexts.Tests/FileStoreSeamTests.cs`），接口三个方法一个都不用改。
- 代价：需要 URL 的调用方要多注入一个接口。这是**刻意的**——
  多出来的那行注入，正是"我在用一个只有对象存储才有的能力"的可见声明。
- 推论：将来若出现第三种存储（例如网络文件系统），先问它属于哪一边，
  而不是给它加第三个接口。
