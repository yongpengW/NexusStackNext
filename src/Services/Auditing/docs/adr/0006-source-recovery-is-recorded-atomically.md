# 来源恢复与恢复记录原子提交

这是 #64 的恢复治理设计。Memory / PostgreSQL 维护端口已实现原子凭据、请求幂等、独立额度、
固定保留期限、有界清理与容量诊断；四个宿主提供独立的查询、条件恢复与凭据查询命令。
公共 Outbox 已按恢复版本拒绝旧投递失败，但一次人工恢复仍须回答是谁、何时、依据哪个状态执行了什么。
不能仅依赖恢复过程中再次尝试写普通操作日志：journal 可能已经满额，正是此时管理员最需要恢复投递。

## Decision

每次成功恢复保存不可变的 RecoveryRecord，与 Outbox 的预算重开和版本递增在同一来源事务中提交。
保存失败或取消则全部撤销，不能留下“已恢复但没有记录”，也不能留下不存在的成功恢复。
记录只含请求身份、消息身份、来源、原停止时间、前后恢复版本、执行身份、固定原因分类及服务端执行时间；
不复制消息载荷、业务参数、凭据或异常正文。失败尝试不得生成成功记录。

PostgreSQL 首次响应返回事务内重新读取的持久化凭据，避免应用时钟精度与数据库时间精度不同，
导致首次响应和后续幂等重放不相等。数据库时间分辨率依据见
[PostgreSQL 日期时间类型](https://www.postgresql.org/docs/current/datatype-datetime.html)；真实数据库测试使用亚微秒时钟验证此差异。

调用方提供稳定的恢复请求 ID。保留期内相同请求及同内容返回原恢复记录，不再改变投递状态；
相同请求 ID 的不同内容拒绝，不能用修改操作者或目标的方式重写历史。重试成功后响应丢失时，
调用方可以安全复用请求 ID；当前投递状态另行查询，不把原恢复记录的成功误称为现在仍 Pending。

恢复记录使用独立有界额度，不占普通观察额度。普通日志满额仍可恢复，恢复记录额度耗尽则拒绝新的恢复，
明确要求清理到期记录或调整管理额度，不覆盖旧记录或在后台丢弃证据。记录保留与源消息清理独立：
清理已交付消息不级联删除恢复记录。到期清理也必须有批次与预算，并原子释放相应额度。
凭据创建时保存不可变的 `RetainUntil`，由本次恢复时刻加 `OperationJournal:Cleanup:RecoveryRetention` 得到，
默认 30 天，允许 1 小时至 365 天。修改配置只影响新凭据，不能缩短已经返回的保留承诺。
达到期限只意味着可以清理；清理真正提交前仍可查询与重放，删除后不声称永久记住请求身份。

当前独立额度为 `OperationJournal:Capacity:MaxRecoveryRecords`，默认 10000，允许 1–1000000。
Memory 在原临界区内检查；PostgreSQL 按请求身份取得事务锁，再取得恢复额度事务锁，
锁定目标消息、检查实际保留凭据数并原子保存。恢复属于低频管理操作，这里以真实记录计数，
不维护第二份可能漂移的累计值。到期清理使用同一额度事务锁，以固定期限和请求 ID 排序，
每批最多 `Cleanup:BatchSize` 条，通过 SaveChanges 与事务提交完成删除；取消或失败不释放额度。
宿主自动维护在同一轮预算内依次清理已交付副本与恢复凭据，两类分别提交事务；
某类失败结束该轮并报告维护降级，下轮继续。已提交的前一类清理不会因后一类失败而被描述为回滚。
同一请求重放在额度检查之前返回已有凭据，满额不会使一个已经成功的请求变成失败。

健康诊断增加 `retainedRecoveryRecords`、`maxRecoveryRecords` 与 `recoveryCapacityReached`；
额度达到上限即报告 Degraded，无须先拒绝一次操作。清理释放额度后可恢复 Healthy，
既有普通采集缺口与维护失败状态仍各自保留其语义，不把控制额度伪装成业务不可用。

维护适配器先采用宿主本地命令，直接操作该宿主的来源 journal；无需启动 Web、配置中心、broker 或业务模块。
它适合边缘或中央调查暂不可用时修复来源，保持服务端口不对外发布的部署不变量。
权限来自宿主执行权限与数据库维护凭据，执行身份记录操作系统提供的账户和主机标签；这些标签不是业务用户认证证明。
命令不接受任意自报业务 Actor，不接受连接串参数，不回显异常正文。连接配置只从环境/受保护配置获得。
后续管理 HTTP 适配器须独立校验显式恢复权限，再调用同一事务端口；调查权限不能代替恢复权限。

### 本地维护命令契约

四个来源宿主在创建 WebApplication、读取配置中心或组装业务模块之前处理 `operation-journal` 命令。
第一条纵向切片是 `operation-journal show <message-id>`：只输出现有交付安全视图，
不输出消息正文或原始失败原因。消息身份必须是非空 UUID，参数数量不符或未知子命令均拒绝，
不能将拼错的维护命令当作普通 Web 启动参数继续启动。

维护命令使用 `ConnectionStrings__OperationJournal` 指定的 PostgreSQL 来源存储；
不会因宿主的开发 Memory 配置而临时创建一份空存储。命令不自动迁移，迁移仍走已有独立入口。
此连接的权限决定可以维护哪份来源存储；Source 是记录的来源信息，不充当访问授权。

| 退出码 | 含义 | 输出约定 |
|---|---|---|
| 0 | 查询完成，或恢复事务已提交/返回同一请求的既有凭据 | stdout 为安全结果 JSON |
| 1 | 配置、存储或执行预算故障 | stderr 只给固定故障码，不回显配置与异常 |
| 2 | 参数无效或未知命令 | stderr 为 `operation_journal.command_invalid` |
| 3 | 目标不存在、状态冲突或恢复额度不足 | stderr 为对应的固定业务错误码 |

恢复命令为 `operation-journal retry <request-id> <message-id> <stopped-at> <retry-revision> <reason>`。
必须显式提供全部条件：两个非空 UUID、含时区的 ISO 8601 停止时间、非负整数版本，
以及 `dependency-restored` 或 `manual-retry` 原因。没有省略并发前提的“强制恢复”，也没有自报 Actor 参数。
恢复响应返回不可变凭据；响应丢失后可原样重试，也可用 `operation-journal receipt <request-id>` 查询。
另一次 show 查询才表示当前交付状态；receipt 不存在可能表示从未恢复，也可能表示凭据已到期清理。

CLI 读取环境中的 `OperationJournal__Capacity__*` 与 `OperationJournal__Cleanup__*`，使用与宿主相同的
选项绑定、默认值和校验；维护进程必须注入该来源部署使用的相同策略。不会自动从配置中心拉取策略，
也不能把命令默认值当成已读取配置中心。配置中心管理的值须在启动维护进程前注入受保护的进程环境。
非法策略在操作前返回固定配置错误，不能先改变状态再失败。系统账户与主机标签由进程读取并写入凭据。

`OperationJournalRecoveryCommandTests` 通过真实四宿主进程与 PostgreSQL 验证：重复请求返回同一凭据、
查询凭据、执行标签、配置额度与期限、过期状态/异内容冲突、非法条件及配置安全失败。

## Considered Options

- 只追加普通 OperationObservation：日志满额时会阻碍恢复，允许丢失时又不能保证恢复留痕。
- 恢复后再写日志：两次提交之间中断会永久丢失记录，重试还可能被当前状态拒绝。
- 只在 Outbox 保存最后操作者：下一次恢复覆盖历史，消息清理会连同恢复证据一并消失。
- 无界恢复历史：控制操作量虽小，仍会绕开已经约定的容量治理。
- 在中央直接读写来源表：打破数据所有权，也使恢复依赖本次可能不可用的中央路径。

## Consequences

成功恢复的公共端口需同时接受请求身份与可信适配器提供的执行上下文；不保留可绕过记录的无审计恢复入口。
Memory 与 PostgreSQL 保持相同事务语义，Memory 仍不承诺进程外持久性。
恢复记录自身不是“原业务提交”的证据，不改变原消息的身份、内容、来源或原发起人。

实现验收包括：满普通额度仍可恢复、满控制额度明确拒绝、记录/状态一方保存失败整体回滚、
并发与丢响应后的同请求幂等、异内容冲突、在途旧失败隔离、源消息清理后仍可查恢复记录、
记录到期后的额度释放，以及真实宿主命令的参数校验、固定安全输出、退出码和异常脱敏。
