# 来源日志按保留记录与载荷限制容量

来源 journal 在 broker 长期不可用时仍持续接受观察，之前没有容量上限；即使 broker 正常，已交付行也一直保留。
默认接受所有观察与有限存储不能同时无限维持，达到容量后的行为必须属于接口契约。

## Decision

同一个 journal 存储共享记录数与 UTF-8 载荷字节额度，包含待投递、死信及已交付但未清理记录。
默认十万条、总载荷 256 MiB、单条 16 KiB，由 `OperationJournal:Capacity` 显式配置。配置不是数据库磁盘配额，
表、索引、WAL、MVCC 旧版本仍需要独立运维预算；这些默认值也不是生产吞吐或容量演练结论。

先验证消息与身份幂等，再为新记录申请额度。同身份同内容仍成功，同身份异内容仍拒绝；满额不能改变这两个语义。
超额返回稳定的 `operation_journal.capacity_exceeded`，单条过大返回 `operation_journal.payload_too_large`，
不保留被拒绝消息的身份，不逐出已有记录，也不伪装成接纳成功。普通采集适配器沿用可观测降级策略：业务响应不变，
失败计数和独立日志健康检查报告缺口。关键业务事实不使用本策略，仍由所属上下文与业务状态同事务保存。

PostgreSQL 使用固定额度行，带条件的 UPDATE 原子申请记录数和字节数，再在同一独立事务插入观察。
失败或取消一起回滚，重投不重复扣额；不在每次写入时全表 COUNT/SUM，也不只依赖某个进程的计数。
并发等待受采集器已有写入预算约束。根据 [PostgreSQL Read Committed 的更新规则](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)，
竞争同一行的更新会等待，并对更新后的版本重新计算 WHERE；本实现用实际并发写入和取消恢复测试验证这一用途。
Memory 使用同一临界区维护记录、消息身份和额度；它仍没有进程外持久性。

`/health/logging` 的 journal 检查报告保留记录数、载荷字节数、对应上限及是否满额。达到总上限时即降级，
不用等下一次采集失败。启动和健康检查还读取额度行，防止仅检查 outbox 就把缺失的治理表当成可用。

## Considered Options

- 每次 COUNT/SUM 后写入：未加锁时有竞争窗口；加全局锁后仍需反复扫描增长中的日志表。
- 进程内计数：重启会丢状态，共用 journal 的其他宿主也可能绕过额度。
- 丢最旧或死信记录给新记录腾空间：无法继续保证已接纳证据，且静默改变故障恢复语义。
- broker 确认就立即删来源记录：缩短身份去重与排障窗口；确认也不等于中央已经保存。
  [RabbitMQ 确认文档](https://www.rabbitmq.com/docs/confirms)分别定义发布确认和消费确认。

## Consequences

所有共用一个 journal 的宿主必须使用一致的容量配置；额度按存储共享，不按 Source 独立计算。
缩小配置不会删除已有记录；已有容量超限时停止新接纳，已有记录仍可去重和交付。
增量迁移回填此前全部记录及载荷；升级时先停用共享该库的旧来源写入者，迁移后统一启动新版本。
不支持旧写入者与新额度逻辑混跑：旧程序不知道要维护额度。

记录数、字节边界、身份冲突、迁移回填、并发、重新建立来源服务及真实 HTTP 降级由
`OperationJournalCapacityTests` 验证；`OperationJournalPersistenceTests` 以仅剩一个额度验证阻断写入取消后可以恢复，
也守住来源独立事务不受业务事务回滚影响。

## 已交付来源副本的清理

来源副本从首次发布确认 `DeliveredAt` 起默认保留一天，允许配置一小时至三十天；不使用消息发生时刻，
否则晚到的旧事件可能刚确认就被删除。重复确认不延长保留；恰好达到截止时刻可以清理，截止后一微秒仍保留。
每轮最多默认 500 条（允许 1–1000），按确认时间与消息 ID 排序，待投递与死信永不进入清理范围。

维护端口 `IOperationJournalMaintenance` 的清理操作只允许执行配置规定的一批清理，不接受任意截止时间、消息内容或删除条件。
PostgreSQL 在独立事务先锁额度行，再取得有界已交付记录；删除及记录数/字节额度释放一起提交。
记录锁使用 `SKIP LOCKED` 跳过正在更新的行；它不消除表锁等待，也不适合用于判断整个队列已清空，
依据 [PostgreSQL 锁定子句说明](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)。
有锁的记录由后续轮次再处理，维护返回零也不能作为“全部清完”的保证。迁移增加对应的已交付部分索引。
Memory 的登记、交付状态、清理和额度共同受同一锁保护，不再维护两份独立 Outbox 状态。

四个来源宿主经 `AddOperationJournalModule` 默认启动后台清理，启动后执行首轮，每轮结束间隔一分钟再尝试。
每轮默认五秒预算；可关闭自动清理，但不会因此移除容量限制。失败、超时和停机取消不提交半次清理；
维护失败计入独立的 `cleanupFailures`，最近失败由 `cleanupDegraded` 报告，后续成功可解除维护降级。
维护恢复不清除普通采集已经造成的缺失计数。诊断不输出异常正文，也不再次产生操作观察。

来源副本到期后，来源不再保留它的幂等身份；相同消息再次提交可能重新排队。消息身份仍不得用于另一份内容，
中央自己的 Inbox、指纹与不可变观察继续拒绝重复或冲突，不能随来源清理一并删除。
`SourceCleanup_DoesNotEraseCentralObservationOrItsDuplicateAndConflictProtection` 验证清理后的重投仍只有一条中央记录。
本决定只管理来源交付副本；发布确认是 broker 接管证据，不证明中央接纳，更不赋予删除中央审计的权限。

`OperationJournalCleanupTests` 还验证批次/时间边界、取消、删除后额度更新失败的整批回滚、并发清理不重复释放、
宿主自动运行与超时恢复。容量准入和来源副本清理不是全部治理：死信恢复、业务事实 Outbox 治理、
中央观察与事实各自的保留约束继续属于 #64，完成全部验收前不关闭日志规格。

## 来源交付状态与受控恢复

同一维护端口提供安全状态查询、有界死信分页和条件恢复。状态投影包含来源、操作与消息身份、阶段、
投递次数及时间；不读取载荷供调查，不返回历史异常正文。历史故障统一转换成固定故障码。
分页按停止时间、消息 ID 排序，页码上限 1000、每页上限 100，可精确过滤来源。
总数和页内容在并发变化时可能不同步，也不承诺跨页快照；管理动作必须重新校验状态。

仅停止投递的记录可恢复，调用方同时回传查询所得的停止时间与 `RetryRevision`。
恢复清除当前尝试预算与故障，保留消息身份、内容、发生时间及占用额度，成功一次才增加恢复版本。
只比较停止时间无法识别“同一时刻再次停止”的新一轮；版本号防止这种旧请求误命中。
PostgreSQL 在独立事务内锁行、校验并通过 SaveChanges 保存；Memory 在同一临界区执行。
没有既有恢复凭据的新请求若状态过期则返回冲突，目标已清理则返回不存在；同一已成功请求重放原凭据。
恢复不修改中央事实或观察。

`OperationJournalDeliveryTests` 验证两种适配器的查询/恢复、旧状态拒绝、同刻再次停止、容量保持、
多人竞争仅一次成功、重建服务后的版本、真实锁等待取消及保存失败回滚。
`RecoveredJournal_CanBeCleanedWhileCentralIsOffline_AndBrokerReplayRemainsIdempotent` 使用真实 RabbitMQ、
来源持久端口和中央宿主进程，验证恢复消息获发布确认后，即使来源副本已清理且中央尚未启动，
中央启动后仍能接收；再次从来源重投不追加中央记录。该测试重建来源服务容器，不声称来源进程崩溃测试。

恢复版本已由公共 Outbox 保存，并用于拒绝旧投递批次的迟到失败；旧一轮的真实确认仍可标记交付。
同一版本也被来源管理接口作为条件使用，避免维护两份可能分离的计数。投递器只统计实际生效的失败状态变更。
两种存储的阻断发布旅程见 `OperationJournalDeliveryTests`，共用规则见 [ADR-0023](../../../../../docs/adr/0023-outbox-failures-belong-to-a-retry-revision.md)。
查询、条件恢复与凭据查询命令已在四宿主开放。恢复凭据与状态原子提交、请求幂等及独立额度见 [ADR-0006](0006-source-recovery-is-recorded-atomically.md)；
恢复记录固定期限、到期清理及运行诊断已实现。
业务事实 Outbox 的容量及清理与中央保留规则仍独立验收。
