# 下次执行时刻由聚合推进，调度器不持有状态

> 重启可靠性的推论已由 [ADR-0002](0002-durable-occurrences-and-business-delegation.md) 取代：无状态循环不等于持久触发，必须同事务登记发生与 Outbox，并由接收方事务去重。以下保留原决定与当时的局限。

`ScheduledTask` 在**每次执行记录之后**推进自己的下次执行时刻。调度器（`ScheduleRunner`）
只是一个循环：问"现在该跑什么"，跑，然后让任务自己往前走。它不缓存"上次跑过谁"。

## 为什么

参照仓库的 `CronScheduleService` 因为**调度键从未写入**而永远静默跳过——
一个不做事的调度器，看起来却完全正常：它在跑、它没报错、它只是什么都没触发。

把"下次该什么时候跑"放进聚合，带来两个直接后果：

1. **调度器的行为可以在测试里被确定地断言**：给定一个时刻和一个任务，
   跑完之后任务的下次时刻必须前进。这不是"大概对"，是可以逐条验证的。
2. **调度器无状态**，因此它崩溃重启后不会重复触发或漏触发——
   它每次都从聚合的当前状态重新判断。

## Considered Options

- **调度器持有"上次执行"缓存**：省一次判断，代价是这个缓存成了唯一的真相来源，
  重启即丢失，而且它无法被领域测试覆盖。
- **由聚合推进（本决定）**：多一次写，换来的是"下次时刻"这条事实有唯一的、可测试的归属。

## Consequences

- 反向验证记录：去掉执行后的下次时刻推进，**3 条测试变红**。
  也就是说这条不变量确实被测试守着，而不是靠约定。
- 时间不作为环境态读取——`ScheduledTask` 接受的"现在"由调用方传入（架构不变量 6 的同一条道理）。
- 当前的任务存储是内存实现，进程重启即丢失，重启后会从初始时刻重新开始。
  那是**存储实现的限制**，不是调度语义的限制；换成持久化实现即可解决，
  而聚合这层不需要改。
