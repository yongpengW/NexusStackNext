# 计划事实与状态共用提交边界

计划创建、规则变化、启停、失败退避、故障清除、重新排期及调度决定都是 Scheduling 拥有的已提交变化。
HTTP 和后台观察描述执行尝试，不能代替这些变化。失败提交、版本冲突和空操作不能写成成功事实。

PostgreSQL 仓储读取本上下文原快照，在 UPDATE 的原版本条件下，将最小事实与计划、决定及可选发生
放入同一次 SaveChanges 事务。读取增加一次查询，但整行 Attach 的修改标记无法证明哪些状态实际变化。
所有失败路径清理跟踪对象，允许在确认失败后同作用域重试。重复同一决定返回既有结论，不创建新事实。
Memory 使用共享状态与同一临界区，所有序列化先于写入；事实上下文和适配器按调用作用域创建，避免共享状态捕获当前身份。

`PlanCommittedV1` 仅含计划标识、最终版本、固定动作、当前执行者和安全执行关联。
triggered / coalesced / skipped 必须携带已登记的决定标识；其他动作不携带决定标识。
直接推进计划状态的存储调用记为 advanced，不凭空宣称登记过决定或完成业务。
同一提交可同时清除故障和记录新决定，两项事实共享最终版本。

调度提交异常后的退避仍在本次执行作用域中保存，因此 deferred 事实能够关联失败观察；
取消继续传播，不登记发生或失败退避。原版本条件防止未知提交结果的退避覆盖已经成功的决定。
未能读取原始来源时不反查中央日志或猜测关联；存储完全不可用时也无法保证退避落库。

事实通过本上下文 Outbox 交付，中央消费者只依赖 Scheduling.Contracts，按固定动作和决定引用组合校验。
OccurrenceDelivery 的重试端口只处理业务触发消息，不接纳审计消息；审计来源恢复及容量治理由 #64 继续完成。
验收使用公开存储端口、HTTP、临时 PostgreSQL 故障和真实进程重启 / RabbitMQ，不以消息类型存在作为完成证据。
