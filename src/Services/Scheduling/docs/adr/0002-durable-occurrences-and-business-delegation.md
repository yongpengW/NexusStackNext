# 先持久登记发生，再由业务上下文接受工作

Scheduling 负责计划定义和触发意图，目标上下文负责接受、输入与执行。一次 Occurrence、计划下次时刻和 Outbox 必须同事务提交；发生身份由计划与单调 TriggerSequence 唯一约束，消息 ID 在可重放事务之外固定。单靠无状态循环与推进时间，不能保证故障后不丢工作；本决定补全并取代 ADR-0001 对重启可靠性的推论。

计划创建时固定目标操作、对象标识和已验证的委托人。首个目标为 `costing.recalculate`，其名称由 Costing.Contracts 声明；Scheduling 不携带金额或任意可执行载荷。Costing 接受时读取自己当前的输入，在同一事务内保存 Inbox、内容指纹、接受或拒绝结论以及自己的持久任务。不存在的对象形成稳定拒绝，不能随重投重新解释；新的业务意图使用新的 Occurrence。

暂停只阻止未来发生，注销只撤销管理会话；已经接受的后台委托继续交付。启停按预期版本提交，固定间隔保持迟到不补跑。操作界面分别查询交付、接受结论与执行结果；Delivered 只表示 broker 接管。相同输入重算可以完成而不改变 Costing / Pricing 的业务版本。

拒绝用计划时刻本身充当唯一身份：暂停/恢复重新安排、未来 Cron 的当地时间重复及存储精度都会造成歧义。拒绝让 Scheduling 同步更新 Costing：那会把业务输入和失败恢复放到错误的上下文。两个平台生产者的 Outbox 各自绑定存储与策略，避免单一 DI 注册覆盖其中一个。

实现与验收由[持久计划触发到 Costing 任务的完整链路](https://github.com/yongpengW/NexusStackNext/issues/43)跟踪。Cron、时区/DST、补跑政策与长任务续租另轮实现；本决定不声称多机高可用部署已完成。
