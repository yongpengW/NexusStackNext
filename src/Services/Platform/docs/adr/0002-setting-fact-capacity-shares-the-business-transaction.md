# 设置事实的容量与业务提交共用事务

#64 要求来源事实在长期 MQ 故障下仍有容量边界。Platform 先实施独立切片：设置变化、
最小事实和容量占用一起提交；额度不足返回固定 `platform.audit_capacity.exhausted`，HTTP 503，
不提交业务变化。已有设置的同值写入不新增事实，因此不消耗额度。

`platform.fact_capacity` 是所属数据库唯一的持久额度账本，宿主启动不修改策略。
实际 Outbox INSERT 的 AFTER 行触发器原子增加保留数量与 UTF-8 Payload 字节数；
条件 UPDATE 在同一额度行上仲裁并发，不先读数量再无条件增加。
事实的 ID、契约名、发生时刻和正文不可原地修改；投递状态更新不改变占用。
DELETE 的 AFTER 行触发器释放对应占用，和删除一起提交。缺少账本时拒绝写入/清理，不推测零占用。

选择数据库触发器是因为 EF 的显式业务事务、隐式 SaveChanges 事务和原始 SQL 清理均须遵守同一规则。
应用拦截器中的独立预留会留下“额度提交而业务回滚”的窗口，进程内计数也不能协调两个宿主。
PostgreSQL 明确保证触发器与触发语句同事务，错误会一起回滚；Read Committed 下并发 UPDATE
等待后在新行版本上重新判断 WHERE。参见 [触发器语义](https://www.postgresql.org/docs/current/trigger-definition.html)
与 [事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)。

默认 100,000 条、总正文 256 MiB、单条正文 16 KiB；待投递、死信和保留期内已确认副本均占用额度。
这些是逻辑记录与正文上限，不是 PostgreSQL 文件大小承诺；索引、行头、失败状态、WAL 和表膨胀仍需运行监控。
清理依 ADR-0024 只删除已确认且过期的事实，不能为了接收新变化驱逐未确认或死信记录。
迁移在同一事务内锁住来源 Outbox 的写入，回填已有副本实际占用并安装触发器，防止两步之间漏算在线写入。
既不删除旧事实，也不因超过新默认额度而失败；超额时暂停新增，等待安全清理。

## Trade-offs and remaining work

每个上下文的一行额度会串行化事实写入的计数更新。这是先保证严格上限的选择，尚未做生产吞吐量验收。
使用现有数据库命令超时与请求取消；专门的准入等待预算仍需在推广阶段验证。
数据库策略避免多宿主配置互相覆盖，但可审计的策略调整入口与容量健康诊断尚未实现；不能建议操作员直接改计数。
测试仅在临时库修改上限，以较少记录暴露边界。

本切片仍局限 Platform PostgreSQL。Memory 对等准入、第二个上下文验证后提取共用实现、其他生产者接入、
专门恢复控制记录和中央归档继续由 #64 追踪，不因本 ADR accepted 而宣称完整治理交付。

`PlatformFactCapacityTests` 的真实 HTTP 测试验证并发争抢最后一个额度、明确拒绝、更新回滚、空操作、
已确认副本清理后恢复写入；持久化边界测试验证 UTF-8 字节、单条/总量限制、触发器故障的占用回滚与固定消息身份。
