# 菜单树是单个聚合，不是一个节点一个聚合

菜单节点的物化路径必须与它的祖先保持一致。把"移动一个节点"做对，意味着要同时改写它**所有后代**的路径。

决定：整棵菜单树作为**一个聚合**（`MenuTree`），节点是聚合内部的实体。
移动、增删都在聚合内部一次完成，不存在"改了父节点却忘了改后代"的中间态。

## Considered Options

- **每个节点一个聚合**：写放大更小、并发更好。但"移动子树"就成了跨聚合操作，
  一致性只能靠调用方记得把后代一并改掉——而**忘记改不会有任何报错**，
  只会让路径与实际父子关系悄悄不一致，直到某个权限查询返回空结果才被发现。
- **不存路径，每次递归查父子**：没有一致性负担，但每次取子树都要递归查询，
  而子树查询恰好是权限推导的热路径。

## Consequences

- 一次移动要加载整棵树。菜单规模是几十到几百个节点，这个代价可以接受；
  如果将来菜单涨到上万节点，这个决定需要重新评估。
- 并发编辑同一棵树会互相冲突。对后台配置来说这是可接受的——
  冲突好过静默损坏。
- 路径以**标识序列**存储与比较，而不是 `LIKE '%id%'`。参照仓库的做法有两个独立缺陷：
  父节点 `1` 会命中 `12`、`21` 的路径（结果错误），且前导通配符让索引完全失效（性能问题）。
