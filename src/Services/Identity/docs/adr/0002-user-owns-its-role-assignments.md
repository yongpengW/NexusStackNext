# 角色归属住在用户聚合里

"这个用户有哪些角色"由 `User` 聚合持有（`User.RoleIds` + `AssignRole` / `RevokeRole`），
**不单独成一个 `UserRoleAssignment` 聚合**。

## 为什么

问题是"谁是这位用户、他能做什么"应该是一次一致的读取，还是两个可以各自变化的事实。

放进 `User` 之后：

- **分配角色是一个事务**（架构不变量 4），不需要为一次管理操作引入跨聚合的最终一致。
- **权限缓存的失效点只有一个**：`UserRolesChanged`。参照仓库的失效路径本来就长
  （review/04 记录了最长 10 小时的窗口），多一个事件源只会让它更难推理。
- **"这个用户的角色"没有第二种答案**。分成两个聚合之后，"用户存在但角色表里没有他"
  这种中间状态就成了可表达的——而在一个权限系统里，可表达就等于迟早会出现。

## Considered Options

- **单独的 `UserRoleAssignment` 聚合**：经典做法，好处是角色分配与用户资料互不干扰
  （写冲突更少），坏处是"用户的角色"变成跨聚合的最终一致读取——
  而授权判定恰好最不能容忍"刚授了权但还没生效"。
- **放进 `User`（本决定）**：多了一次聚合写，换来授权判定永远看到一致的快照。

## Consequences

- **代价是真的**：一个拥有大量角色的用户会让这个聚合变大，每次分配角色都要整聚合写。
  触发条件写在这里：**如果"每个用户的角色数"稳定超过几十，就重新评估这条决定**——
  在那之前，角色数是个位数，整聚合写比跨聚合一致更便宜。
- `AssignRole` / `RevokeRole` 在集合没有真的变化时是**空操作且不发事件**。
  这条与 `Role.Grant` / `Role.Revoke` 一致：无谓的失效事件会让缓存的行为无法推理。
- 授权判定的链路因此是：`User.RoleIds` → 各 `Role.GrantedMenuIds` → 菜单/API 资源上的路由模板
  → 权限键集合 → `AccessPolicy.Decide`。这条链路上的每一段都已有测试。
