# 安全状态事实来自实际提交

Identity 的业务事实描述拥有数据的聚合实际提交的变化，以内部标识和提交版本为客体。
不能从 HTTP / 命令结果推断是否提交：错误密码返回失败，却仍然提交失败计数或 Lockout；
正确密码因已锁定被拒绝，则没有新的状态提交。原发起关系只用于调查，不能替代当前认证的 Actor。

PostgreSQL 保存适配器在同一次 SaveChanges 中添加明确映射的最小契约到 Identity Outbox。
它读取实际跟踪变化，既不复制实体属性值，也不序列化领域事件。事实写失败会让该次业务保存失败；
同一存储作用域重试前须清理本次失败的暂存事实。跨上下文只传 `Identity.Contracts`，由中央 Auditing
按已知客体及动作接纳。接收端不查询 Identity 的表，也不能替来源补造提交事实。

选择显式提交映射的原因是领域事件覆盖与持久变化覆盖并不等价：例如 RefreshToken 消费会改变状态但没有领域事件，
另一些事件包含用户名或自由文本，不能直接对外发布。按处理器逐个追加消息也容易漏掉拒绝后保留安全状态的路径。
代价是每项变化都要有映射和行为验证；新的聚合不会因为继承基类就自动拥有完整事实历史。
User 的账户维护、登录与会话状态，Role 的名称、平台及授权，MenuTree 的节点变化，ApiResource 登记，
RefreshToken 的签发、消费和撤销已接入 PostgreSQL。集合撤销必须读取已删除的所属关系行；
只读当前集合会漏掉撤销最后一项。菜单节点变化归于树根及提交版本，不能将节点伪装成独立聚合。

User/Role 的权限关系按实际增删的内部标识逐项记录，RefreshToken 带所属 User；创建时已有的授权也必须保留。
EF 对集合的先删后加未必改变最终成员，因此同一标识的增删需抵消，不能伪造撤权再授权。
关系事实与根使用相同的提交版本；它不把关联客体并入根的事务边界。

MenuTree 逐节点区分增删、改名、排序与移动，子树后代的路径变化记为祖先变化；各项只引用内部 Menu 标识。
删后重建同一节点按提交前后内容比较，不能把物理替换写成删除再新增。ApiResource 可引用所属 Menu。
登录成功的状态变化还包含失败计数清零/解除锁定，不要求最后登录时间一定改变。
Memory 适配器的工作副本、提交与重试语义见 [ADR-0005](0005-memory-storage-has-a-commit-boundary.md)，
已接入相同最小契约。逐项证据及完整故障验收仍见[覆盖矩阵](../../../../../docs/committed-audit-coverage.md)。
当前登录/刷新用例的多聚合事务是既存建模问题，日志接入不改变或宣称解决该问题。
