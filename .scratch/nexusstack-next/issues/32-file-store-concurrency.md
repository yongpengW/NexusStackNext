# 32 — 路由表文件存储的并发缺陷，以及"原子写"这个词的误导

Status: resolved
Type: task
Labels: ready-for-agent
Blocked by: 26

> **2026-09-29 说明**：本票来自一个**不稳定的测试**——全量并行跑时偶发变红，单独跑从不红。
> 查下去发现的是产品代码里的真缺陷，而"原子写"这个说法本身也需要更正。

## 缺陷一：读流量一稳定，写者就永远写不进去

上一版用 `File.Move(source, destination, overwrite: true)` 做替换。
**实测**：只要读者持有目标文件，它就抛 `Access to the path is denied`——即便读取方已经
按上一轮的结论允许了 `FileShare.Delete`。

后果的形态很难查：**不是偶发失败，而是读流量一稳定，写者就永久失败。**

修法：改用 `File.Replace`（Win32 `ReplaceFile`），它就是为"替换一个可能正被打开的文件"设计的；
目标不存在时退回普通 move，外面再包一层重试。

## 缺陷二：测试忽略了写者的结果

旧测试只收集**读者**的失败，写者的返回值直接丢掉。于是"写者一直失败、测试却绿"是可能的。

现在两边都断言。

## 更正：`File.Replace` 也不给读者"连续"的视图

修完缺陷一之后，读者开始报两种错：

```
read_failed: 读取路由配置失败：The process cannot access the file because ...
file_missing: 路由配置文件不存在：...
```

**`file_missing` 是关键**：替换期间目录项是**空窗的**。所以 `File.Replace` 从读者视角
**并不原子**。

于是把契约写准确，写进类型文档：

| 保证 | 不保证 |
|---|---|
| 读者**永远读不到"写了一半"的文档**（内容完整性） | 读者不会观察到替换的瞬间（目录项连续性） |

读取侧在**有限预算**内重试，超出预算就返回明确失败。
**"读不到就报错"比"无限等待"好**——这是一个配置文件，不是关键路径。

**"原子写"这个词会误导**：它让人以为连"看见旧还是新"都保证了。
它保证的只是内容不会被读成半个。

## 缺陷三：一个测不住的测试

旧测试用 2 秒墙钟计时，并断言"读者一次都不许失败"——**比实现保证的更强**，
于是在并行负载下偶发变红。

**复现不了的不稳定测试比没有测试更糟：它会训练人忽略红色。**

改法：
1. **固定迭代次数，不用墙钟**——可复现。
2. 断言改成真正契约：写者必须成功；读者**绝不**拿到 `gateway.json.malformed`；
   瞬时失败计数但不致命。
3. 保留"读者至少成功过一次"——零个对象不等于通过（票据 30 的教训）。

**验证**：全量测试连跑 **4 遍全绿**（此前 2 遍里挂 1 遍）。

## 产出

- `FileRouteTableStore.cs`：`File.Replace` + 重试 + 读取侧预算内重试 + 契约写进类型文档
- `FileRouteTableStoreTests.cs`：`ConcurrentReads_NeverObserveAPartialDocument`

## 这一票的形状

三个缺陷是**顺着一条线**找出来的：不稳定测试 → 忽略的返回值 → 用错的文件原语。
每一步都只有在前一步被修掉之后才暴露出来。

**如果不稳定测试当初被"重跑一次就过了"糊弄过去，这三条都不会被发现。**
