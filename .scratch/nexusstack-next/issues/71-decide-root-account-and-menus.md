# 71 — 决定：根账号从哪儿来，菜单从哪儿来

## Question

票据 67 的授权链断在第一环，而它断掉的原因**不是实现缺失，是两个没有做的决定**。
这一票只解决它们，不写任何实现。

**一、第一个根账号从哪儿来？**

`IsRoot` 那条旁路（`AccessPolicy.Decide`）现在**不可达**——
它有测试，但没有真实用户能走上去：`User.Create` 的 `isBuiltIn` 参数永远是 `false`。

1. **启动时按配置播种**：宿主读一组环境变量（用户名 + 口令哈希）建内置账号，已存在则跳过。
   最简单；代价是"配置文件里有一个能进一切的账号"，而这需要写进部署文档、并在轮换口令时有流程。
2. **一次性 CLI**：`dotnet run --project … -- create-root --user X`，不进启动路径。
   生产上更干净；代价是多一条**必须被记住**的命令，忘记执行的后果是"新环境没有任何人能授权"。
3. **首个注册者即根**：第一个 `POST /users` 的人成为根账号。
   零配置；代价是把"谁先注册谁说了算"变成一个**竞态**——而它发生在暴露到公网的第一秒。

**二、菜单从哪儿来？**

`MenuTree.AddRoot` 在领域层存在且被测过，**没有任何地方调用它**。
于是：菜单建不出来 ⇒ api-resource 挂不上 ⇒ 角色授不到菜单 ⇒ 权限集合永远为空。

1. **加一组菜单管理端点**（就是现在缺的那一环）。代价：多一组要授权的写端点，且它本身需要权限键。
2. **当种子数据随部署导入**。代价：要定格式（JSON？SQL？）、要定"重跑一次会不会重复导入"、
   且运营改一次导航要发一次部署。
3. **暂时去掉菜单这一层**，让 api-resource 直接挂到角色上。
   代价：丢掉"按后台导航组织权限"这个能力，且这是一次**领域模型变更**（要 ADR）。

## 为什么这必须由人决定

三条路都"能用"，分歧不在实现难度，而在**运维形态与安全后果**：
有没有一个能进一切的账号、有没有一条必须被记住的命令、谁先注册谁说了算——
这三件事的后果落在**部署**上，不落在代码上。agent 替人选一个，等于替你把部署形态定了，
而票据 67 的验收标准里**没有一条能验证这个选择对不对**。

> wayfinder 的类型说明：`grilling` 是 **HITL**——只能在与人的实时对话里解决。
> **agent 不得替人回答自己提出的问题**（自己答完再自己实现，等于把决定权悄悄收走了）。

## 决议之后

- 选定的选项与理由写进本票的 `## Comments`（那是它唯一的家）；
- 需要的实现落成票据 67 的任务，67 随即可开工；
- 若选"暂时去掉菜单这一层"，则要新开一张票并配 ADR——**67 的验收标准随之改写**，
  而不是照原样实现一遍再发现它没有意义。

## 不在本票范围内

任何实现。本票只产出一个决定。

## Comments

### local

**决定（2026-09-30，人选，agent 不代为回答）**

- **根账号 →「启动时按配置播种（存在则跳过）」**。
  理由：模板开箱可用；幂等；与既有的"必需配置"形状一致——宿主读不到必需的配置时**明确失败**
  而不是静默降级。代价写进 67 的验收：部署文档必须写明"存在一个能进一切的账号，以及怎么轮换它"。
- **菜单 →「加一组菜单管理端点」**。
  理由：67 的验收是一条**真实 HTTP 旅程**，而种子数据那条路要先定格式与"重跑会不会重复导入"，
  且运营改一次导航就要发一次部署；去掉菜单那一层是**领域模型变更**（要配 ADR，并改写 67 的验收）。
  菜单管理端点**只允许根账号**调用：菜单管理的权限键还没有登记，而 `IsRoot` 那条旁路
  正是为这种"引导期"存在的——它此前不可达，就是因为没有根账号。

### local

**一处实现细节上的偏离（记下来，不藏）**

选项的措辞是"用户名 + **口令哈希**"；实现改为读**用户名 + 口令**，在播种那一刻用注册的
`IPasswordHasher` 当场哈希。理由：本仓的口令哈希是 Pbkdf2 带**随机盐**，人手算不出可复现的值；
而口令本来就和其它凭据一样住在 `env/*.dev`（gitignored）或配置中心里，安全性质相同
（哈希本身也是可用来登录的凭据，泄露它的后果不比泄露口令轻）。
这一条写在这里，是因为"和选项不一样"必须是有意为之，而不是没人注意。
