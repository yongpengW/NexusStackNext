## 一、健康检查：**自己活着 ≠ 依赖可用**

**改之前**：六个宿主只有一个 `/health`，只报自己的状态。
**后果**：网关在**所有后端都挂掉时仍然报健康**，编排系统会继续把流量送进来。

**改之后**：

| 端点 | 含义 | 查依赖吗 |
|---|---|---|
| `/health`、`/health/live` | 进程还能应答 HTTP | **不查**——查了会导致依赖抖动时容器被反复重启 |
| `/health/ready` | 依赖可用 | **查** |

### 检查只加在真正有依赖的两处

| 宿主 | 就绪检查 | 为什么 |
|---|---|---|
| **Gateway** | 每个 cluster 至少一个目标可达（探目标的 `/health/live`） | 它的依赖就是后端 |
| **Files** | 存储端口**写一个探针再删掉** | 磁盘满了、权限变了、对象存储挂了，它此前都会照样报健康 |
| 其余四个 | 无 | **它们目前确实没有外部依赖**（存储是内存适配器）。ready == live 是事实，不是偷懒 |

Files 那条探的是**端口本身**而不是实现内部（比如"磁盘根目录可写"）——
换成本地磁盘、对象存储、别的实现，这条检查都不用改。**端口没变，它就还有效。**

网关那条探的是目标的 `/health/live` 而不是 `/health/ready`：
后者会让两个就绪状态互相依赖，上游只想知道"这个目标还接不接得上"。
另外它按**"至少一个目标可达"**判定——多副本时挂一个不该让整个就绪变红。

### 实跑验证（决定性的一条）

```
六个宿主 live=200  ready=200
停掉 Platform  -> 网关 /health/ready = 503，/health/live 仍 200
重启 Platform  -> 网关 /health/ready 恢复 200
```

**就绪检查现在真的有含义了**：它会在依赖消失时变红，也会在依赖回来时恢复。
