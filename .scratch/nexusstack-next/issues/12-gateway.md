## 要做什么

`src/Gateway/NexusStackNext.Gateway`（YARP，ADR-0003）。网关**不持有数据、不持有业务判断**：

- **验签**（认证），不做授权——授权在各上下文（ADR-0003）。
- **限流**、**关联 ID 生成并贯穿**（原项目完全没有关联 ID）。
- 路由/集群的增删改查 API，且**必须鉴权**。原项目的这套 API 因认证方案未注册而必然失败：
  `ApiControllerBase.cs:16` 硬编码 `Authorize(AuthenticationSchemes="Authorization-Token")`，
  而该方案只在 WebService 分支注册（`Core/ServiceCollectionExtensions.cs:179-182`），网关只调了 `AddAuthorization()`（`:209`）。
- **路由持久化**：不放 `AppContext.BaseDirectory`（原做法每副本一份、非原子写、仓库里那份还是死文件）。
  改用平台库或配置中心，并保证多副本一致。
- 配置转换**不得丢弃字段**：原 `ConvertConfig`（`DynamicProxyConfigProvider.cs:102-152`）丢掉了
  Transforms / HttpRequest / HttpClientConfig。
- 补齐：被动健康检查、超时、重试、熔断、负载均衡。
- **不依赖全栈基础设施**：原网关因共享管线里无条件 `UseRedis`（`Core/ServiceCollectionExtensions.cs:295`）
  而在生产配置缺失时直接启动失败。新网关只依赖它真正需要的东西。

## Comments

### local

**第 8 轮完成**

#### 交付：路由表管理 API

`GatewayRouteAdmin`：`GET /gateway/routes/{routeId}`、`POST`、`PUT`、`DELETE`。

**只认根管理员**（策略 `gateway-route-admin`）。这里不做业务授权（ADR-0003），
但"谁能改路由表"不是业务授权——它是网关**自己的**管理边界。改一张路由表是系统级动作：
加一条路由等于把某个上游暴露到边缘上。

参照仓库的这套 API 因为认证方案没注册而**必然失败**——那段代码从来没真正工作过，
而"从来没工作过"与"被正确保护"在日志上看起来一样。

#### 热重载：没有它，"保存成功"就是谎话

网关原先 `LoadFromMemory`（启动时拷一份），之后改磁盘上的路由表对运行中的进程毫无影响——
管理 API 会返回 204，而流量照旧走老规则。改成 `InMemoryConfigProvider` + `RouteTableReloader`。

#### 测试抓到了我自己引入的同一个失效

`/gateway/routes`（自述端点）第一版读的是**构造时捕获的快照**——于是管理 API 改完之后，
它还在报旧表，而**看自述端点也看不出来**（它跟着一起说谎）。改成每次读存储。

#### 两次"上移到 BuildingBlocks"的判断

按不变量 7（第二个消费者之后才上移）：

| 东西 | 消费者 | 结论 |
|---|---|---|
| `NexusStackClaims`（声明名） | Identity 签发、平台宿主读取、**网关验签** | 三个 → 上移 ✓ |
| `JwtOptions` | Identity 签发、**网关验签** | 两个 → 上移 ✓ |

两者的失效形态相同：**一边改了、另一边没改**，症状是"令牌明明签出来了却验不过"，
而它看起来像认证配置问题，不像"两边用了不同的默认值"。

网关**不引用 PlatformHost**——那是反向依赖。声明名与配置形状因此必须住在共享层。

#### 还剩什么

**多副本一致性没做。** `FileRouteTableStore` 的写入是原子的，但每个副本各持一份文件，
多副本会各自漂移。票据要求"改用平台库或配置中心"——那是另一件工作，
所以本票标 `claimed` 而不是 `resolved`。

一个顺带记下的取舍：路由**集群**的 CRUD 没做（票据说"路由/集群"）。路由是实质，
集群是它的前提；而集群改动会牵动 YARP 的目标列表与健康检查，值得单独一轮。


### local

**第 13 轮：多副本那条的约束分析**

#### 票据给的第一个选项，被票据自己的另一条验收否掉了

原文写着「改用**平台库**或配置中心」。而"平台库"要求网关引 EF Core——
那直接违反**同一张票据**的另一条验收：

> **不依赖全栈基础设施**：原网关因共享管线里无条件 `UseRedis` 而在生产配置缺失时直接启动失败。
> 新网关只依赖它真正需要的东西。

实测：网关当前的依赖里**没有任何 EF / Npgsql**（只有 YARP、JwtBearer、OpenApi、SwaggerUI
与两个自建工程）。加一个数据库实现就是把它推回参照仓库那个形态。

**所以两个选项里只剩配置中心。** 这不是偏好，是同一张票据内部两条验收互相约束的结果。

#### 配置中心那条：正确的方向，但有一个具体的阻塞

设计是清晰的，而且比"两个副本共享一个数据库"更贴合多副本：

> 把路由表作为一个配置项发布到 AgileConfig → **每个副本各自轮询并收敛** →
> 它们不需要互相知道对方存在，"一致"是**构造上**成立的，而不是靠写者小心。

实测：AgileConfig 服务端在 `<服务器IP>:8010`，管理界面可用。
但**发布**走的是它的**管理 API**，需要管理员凭据——而我没有。

所以这条升级路径**被凭据挡住**，不是被技术挡住。需要你给一组 AgileConfig 的管理凭据
（或者明确说不需要这条路径）。

#### 为什么现在可以结票

验收的原文是「有测试**或明确的单写者设计**」。后者已经成立，且是**写在类型上**的：

> 这是单机默认实现。多副本部署时"每个副本各有一份文件"仍然成立，
> 因此它只适合单写者场景；多副本请替换为配置中心或数据库实现（端口就是为此留的）。

**"明确的单写者设计"是一个显式的取舍，不是一个疏忽** —— 而升级路径只有一个端口之隔。
