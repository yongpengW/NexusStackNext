> 前三个上下文的存储都是**内存**实现。Files 不一样：它的字节存储是**本地磁盘**——
> 一个生产形态的适配器，而不是开发占位。票据 27 验证过的那道缝，现在第一次有真实调用方。

## 实跑结果

```
健康检查                        -> HTTP 200
上传 hello.txt                  -> HTTP 201  {"size":16,"storageKey":"aa04feb5…"}
磁盘上确实有这份字节            -> True（16 字节）
下载                            -> HTTP 200  "hello nexusstack"
元数据                          -> HTTP 200  {"size":16,"stored":true}
非法文件名 ../../etc/passwd     -> HTTP 400
下载不存在的文件                -> HTTP 404
删除                            -> HTTP 204
删除后下载                      -> HTTP 404
删除后磁盘上的字节也没了        -> True
```

**"磁盘上确实有"与"删除后也没了"这两条是重点**：它们证明的不是 HTTP 契约，
而是**字节真的经过了存储适配器**，而不是停在内存里。

## 存储句柄 → 路径的解析是一处真实的攻击面

句柄由本类生成，看起来"无所谓不可信"。但一旦它来自外部（迁移脚本、数据库被改、
将来的管理接口），`../../` 这类值就会让读写落到存储根目录之外。

因此解析时**两道闸**：

1. 句柄本身不许含分隔符、`..` 或 NUL；
2. 拼出来的绝对路径必须以存储根目录开头（带分隔符，避免 `store-evil` 命中 `store`）。

第一道闸在正常路径上永远不会触发——**它防的是"正常路径"这个假设本身**。

## 写入与删除的顺序都是刻意的

| 操作 | 顺序 | 最坏情况 |
|---|---|---|
| 上传 | **先写字节，再标记已存储** | 留下一份无人引用的字节（可被清理回收） |
| 删除 | **先软删元数据，再删字节** | 同样留下字节 |

两边都选了**同一个失败方向**。反过来会得到一种很难查的状态：
元数据说"已存储"，而字节根本不在——那会以 500 的形式出现在下载路径上，
而不是在写入时立刻暴露。

## `LocalDiskFileStore` 刻意不实现 `IFileUrlProvider`

磁盘给不出有期限的可访问链接，所以那个接口不在它身上。
这是 `docs/adr/0001-store-and-url-provider-are-separate.md` 的决定
**在真实适配器上的第一次兑现**：做不到的能力不给接口。

调用方要 URL 就必须显式依赖 `IFileUrlProvider`——依赖关系本身就是能力声明。
