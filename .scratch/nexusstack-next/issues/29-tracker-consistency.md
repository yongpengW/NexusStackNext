# 29 — 跟踪器一致性检查：把"我们做了什么"变成被检查的声明

Status: resolved
Type: task
Labels: ready-for-agent
Blocked by: 28

> 本票是票据 28 那条教训的推广：**一句关于"我们做了什么"的声明，如果不受检查，
> 就会在没人注意的时候变成谎话。** 票据 28 处理的是测试覆盖声明；本票处理跟踪器。

## Answer

**产出（1 个脚本 + CI 接入）**：`scripts/check-tracker.ps1`

八项检查：

1. 每张票据都有 `Status` / `Type` / `Labels` / `Blocked by`
2. `Status` 是五个规范角色之一
3. `Blocked by` 引用的票据**真实存在**
4. 已 `resolved` 的票据**不得仍被未解决的票据阻塞**（自相矛盾）
5. `map.md` 的票据索引与 `issues/` 下的文件**双向**一一对应
6. 每个上下文都有 `CONTEXT.md`、至少一份 `docs/adr/`、一个宿主
7. `CONTEXT-MAP.md` 提到每一个上下文
8. 每个 ADR 目录的编号连续，无跳号

## 第一次运行就抓到一个真实矛盾

```
跟踪器检查发现 1 个问题：
  [依赖矛盾] 票据 17 已 resolved，却仍被未解决的 15 阻塞
```

票据 17 在 15 轮前交付时，我只做了不依赖测试库的那一半，把状态改成 `resolved`，
**却没改 `Blocked by` 字段**——它仍写着 15。两个字段互相矛盾，就这样活了 15 轮。

这不是"我记性差"，而是：**没有任何机制会在没人看的时候响。**
跟踪器读起来像结论，所以它最容易被当成结论。

## 反向验证（三类变异）

| 变异 | 脚本输出 |
|---|---|
| `Status: resolved` → `done` | `[票据状态] 24-gateway-host.md 的 Status 'done' 不是五个规范角色之一` |
| `Blocked by: 23` → `99` | `[依赖引用] 票据 24 依赖 99，但没有这张票` |
| 从地图索引删掉票据 26 那行 | `[地图索引] 票据 26 存在，但 map.md 的票据索引里没有它` |

三类都精确命中且**只**命中对应项。改动已还原，并做了**字节级核对**（`SequenceEqual` = True）。

## 一个实现细节

脚本第一版用了变量名 `$host`，PowerShell 直接拒绝：

```
无法覆盖变量 Host ，因为它是只读变量或常量。
```

改名 `$hostProject` 并留了注释——下一个人不会再踩。

## 收尾

```
跟踪器干净：28 张票据、5 个上下文、6 个 ADR 目录，全部一致。
```

已接进 CI。**本机可执行，所以这一次不是"已写未验"**——
与 `ci.yml` 本身不同，它的输出是当场跑出来的。
