**针对参照仓库的什么**

参照仓库把 `proxy-config.json` 放在 `AppContext.BaseDirectory`（`JsonProxyConfigStore.cs:44`）：
**每个副本各一份**、写入**不是原子的**（`EnsureConfigFileExists:47` 还在 `try` 之外）、
而仓库里那份配置文件**根本没有任何 csproj 引用它**——一个死文件。

新实现：端口 + 原子写。多副本那条限制**写在类型上**而不是文档里：

> 这是单机默认实现。多副本部署时"每个副本各有一份文件"仍然成立，
> 因此它只适合单写者场景；多副本请替换为配置中心或数据库实现（端口就是为此留的）。

**运行时抓到的一个真问题：原子写要求读取方配合**

第一版用 `File.ReadAllTextAsync` 读、`File.Move(overwrite: true)` 写。
并发测试（2 秒内持续写 + 持续读）**红了**，而且是写者失败——原因不是"读到了半个文件"，
而是：

> **Windows 上，`MoveFileEx` 覆盖一个正被打开的目标会失败（共享冲突）。**
> 读者越多，写者越容易失败。

修法是读取时以 `FileShare.Read | FileShare.Delete` 打开：读者继续看到旧文件的完整内容，
写者的 rename 也能顺利执行——**这才是原子写真正要的语义**。

这条不写下来，下一个人会以为"原子写 = 写临时文件再 rename"就够了。
实际上它还需要读取方允许被替换。

**并发测试验证的性质**：2 秒内持续读写，**读者从未读到无法解析的文档**——
要么完整的旧内容、要么完整的新内容。

**一条环境相关的测试改动（不是产品问题）**

测试原本用 `Path.GetTempPath()` 建临时目录，在受限环境下被拒绝写入
（`Path.GetTempPath()` 给的是长路径，而通行的是短路径形式）。
改为使用测试输出目录，并在注释里写明**不要"顺手"改回去**。

**实跑验证**

```
网关 /health        -> HTTP 200
网关 转发公开路由    -> HTTP 200    （路由表经新存储载入）
受保护路由          -> HTTP 401
输出目录 .tmp 文件数 -> 0
```
