# 59 — 生产也要能看文档：在网关聚合各后端的 OpenAPI

Status: resolved
Type: task
Labels: ready-for-agent
Blocked by: 58

> 用户改主意了：不要只在 Development 看文档，**生产也要看**——
> 那就得让网关聚合各后端的文档（微服务的标准做法）。

## 为什么这是自洽的

票据 58 把界面关在 Development，理由是"业务服务不对外暴露，边缘是唯一入口"。

**但网关就是边缘。** 在边缘上暴露文档是产品决定，不是绕过——
而挂在业务服务上才是绕过。所以两种处置各自成立：

| 宿主 | `/scalar/v1` | 理由 |
|---|---|---|
| **平台宿主** | **仅 Development** | 它会绕过边缘暴露全部 API 面 |
| **网关** | **总是开（含生产）** | 它就在边缘上，这正是要暴露的地方 |

## 实现

```
网关自己的文档  →  /openapi/gateway.json      （内部路径，聚合器去取它）
聚合后的文档    →  /openapi/v1.json           （对外）
来源状态        →  /gateway/openapi/sources   （哪些来源取到了、各多少条路径）
参考界面        →  /scalar/v1                 （总是开）
```

**所有来源统一走 HTTP，包括网关自己。** 一套代码路径，没有"自己"这个特例。

### 一个失败不会让整份文档挂掉，但**不会被藏起来**

来源取不到时：记警告、该来源计入状态、其余照常合并。
`/gateway/openapi/sources` 把状态直接暴露出来：

```json
{ "complete": false,
  "sources": [ { "name": "platform-host", "ok": false, "pathCount": 0,
                 "detail": "由于目标计算机积极拒绝，无法连接。 (127.0.0.1:5191)" } ] }
```

**"文档少了几个接口"必须是看得见的**——否则它与"接口本来就不存在"分不开，
而后者会让人以为服务没实现。

### schema 名一律加来源前缀

两家后端各有一个叫 `ProblemDetails` 的模型时，直接合并会让其中一家的 `$ref`
指向另一家的结构——**而且不会报错**，只是文档里的字段悄悄错了。
两边同时改名让它在结构上不可能发生，顺带让"这个模型来自哪个服务"看得见。

## 我在这一处连改错两次，都是靠"看输出"抓到的

**第一次**：前缀改写作用在一份**被丢弃的文本**上——`$ref` 改了、schema 键没改，
而取路径时用的又是原对象。结果"改与不改正好一致"，看不出任何差别，文档也没坏。
**是那句"schema 带来源前缀的: 0"暴露的。**

**第二次**：改成在克隆对象上改名，但**顺序反了**——先拷 `paths`、后改名，
拷出去的那份留着旧引用。文档里出现 **7 个指向不存在模型的 `$ref`**。
**是"悬空引用 vs 未被引用的 schema"这组对照暴露的。**

两次都不是编译错误，也都不影响服务启动——**只有检查聚合出来的文档本身才能发现**。

## 验证（Production 环境）

```
Hosting environment: Production
/openapi/gateway.json    200
/openapi/v1.json         200   路径 23 条 = 网关 3 + 后端 20
/gateway/openapi/sources complete=true   gateway(3) / platform-host(20)
/scalar/v1               200   ← 生产可用，用户的要求
/gateway/routes          经边缘的策略不变：公开 200 / 需认证 401
schema 悬空引用           无        未被引用的 schema  无
```

**负向验证**：停掉平台宿主 → 文档**仍返回 200**（只剩网关自己的 3 条），
`complete=false` 且失败原因可见。**降级，但不静默。**
