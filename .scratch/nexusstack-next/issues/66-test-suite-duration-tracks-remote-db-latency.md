## 真实因果链

```
13 个测试工程并行跑（全部连同一台 PostgreSQL）
        ↓
DDL 风暴：反复建表 / 删表 / 重跑十一张表的迁移
        ↓
pg_catalog 膨胀 + 大量必须 fsync 的脏页
        ↓
checkpoint 从毫秒级变成 236～336 秒（单个 fsync 最长 8.7 秒）
        ↓
数据库不可用
        ↓
AgileConfig 连不上库 → **Unhandled exception → 进程崩溃**
        ↓
容器重启策略把它拉起来 → 又连不上 → 又崩
        ↓
崩溃重启循环：每次重启都要重新读镜像层与 .NET 运行时
        ↓
**磁盘读被吃满** → 数据库 WAL 重放走不完 → SSH 卡死
```

用户发现的关键证据是 AgileConfig 容器日志：

```
Unhandled exception. System.Exception: Failed to connect to <服务器IP>:5432
 ---> SocketException (111): Connection refused
 at Microsoft.AspNetCore.Hosting.WebHost.StartAsync(...)
```

**`Unhandled exception` 是关键**：它不是"一直重试"，而是**直接崩**，然后由容器的
`restart` 策略无限拉起——循环发生在**编排层**，不在应用层。

## 我错了两次，错法不一样

### 第一次：把"时间吻合"当成了因果

我看到测试跑的时间窗和磁盘饱和吻合，就说"是我的问题"。
**时间吻合不是因果**——而我手里当时已经有反证（写几乎为零），却没去看。

### 第二次：用了一个分不出"空闲"和"已死"的测量

我量到"PostgreSQL 读盘 0 MB/s"，据此宣布"不是我"。

**但读 0 同样意味着它可能根本没在运行。** 那台库当时确实已经被压垮了。
我拿一个**无法到达真相的验证**去下结论——这正是本仓反复记录的那个失效模式。

正确的下一步当时就在手边：连不上就该问"**它为什么连不上**"，
而不是"它读了多少"。

## 修了什么

### 一、测试不再并行（`scripts/run-tests.ps1`）

`dotnet test <解决方案>` 默认并行跑十几个工程，**而 `-m:1` 不管用**——
实测过一次：加上它之后仍然同时起 13 个进程（`-m:1` 限制的是构建并行度，
不是测试宿主的启动并行度）。

改成**逐个项目循环**，实测并发峰值 = 1。

### 二、迁移从 21 次降到 1 次

`IdentityDatabaseFixture`（xUnit 集合 fixture）：初始化时删一次 schema、迁一次
（所以"迁移可对空 schema 执行成功"仍然被真的验证，只是从二十来次变成一次），
测试之间用 `TRUNCATE`。

`TRUNCATE` 与重新迁移的差别不是"快一点"：前者只动数据页，后者每次都要写十一张表的
目录项与索引——**而目录膨胀正是这次事故的机制**。

### 三、跑之前先看清要压哪台机器

脚本现在会打印目标数据库主机，并要求确认——因为**那台库不只我们在用**
（AgileConfig 也用它）。这条是这次事故里最缺的一环：
**我跑全量之前没有问过"这台库还有谁在用"。**

### 四、清理泄漏

- 杀掉测试进程后残留的 `idle in transaction` 会话（它们**持锁**，会让后续 DDL 卡住）
- 关掉 MSBuild 常驻工作节点：**命令行参数 `-nodeReuse:false` 无效**，
  必须用环境变量 `MSBUILDDISABLENODEREUSE=1`（父进程收下参数，派生节点仍写着
  `/nodeReuse:true`）

## 顺带记下的一条：共享数据库没有隔离

本仓的集成测试连的是**一台共享的、还有别的生产服务在用的** PostgreSQL。
`env/test.dev` 里那一个连接串同时是"测试库"和"配置中心的库"。

**这不是测试的错，是环境的事实**——但测试代码里没有任何地方体现它。
下次要跑全量之前，先确认那台机器上还有谁。
