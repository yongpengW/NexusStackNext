### 原始的三个选项（保留，供追溯）

原项目是**自研 JWT + 自建 Token 表**；但你的 git 里有一个 `dev-authentik` 分支，说明考虑过接外部 IdP。

- **B. OpenIddict**：标准 OAuth2/OIDC，授权码 + PKCE，与网关验签天然契合；引入一个较重的依赖。
- **C. Authentik / 外部 IdP**：身份托管出去，Identity 上下文只保留用户档案与权限；但要接受"用户主数据不在自己库里"。

## 要做什么（形态确定后）

- access + refresh 双令牌；**refresh 只存哈希**、**一次性使用**、每次刷新轮换（修正原项目明文 + 可重放）。
- 登录防护：**验证码校验**（原项目写了 `ValidateCaptchaAsync` 却零调用）、失败计数与锁定、速率限制。
- 错误信息**不区分**"用户不存在"与"密码错误"（原项目会分别返回"账号或密码错误"与"该用户还未设置密码"，泄露用户是否存在）。
- 令牌撤销要能立即生效，走票据 11 的版本号失效机制。

## 验收标准

- [x] 同一 refresh token 用第二次必须失败，且**第一次签发的 access token 不受影响**（轮换语义）——`TokenIssuanceTests`，真库。
- [x] 数据库里不存在任何明文 refresh token（有测试断言）——断言方式是**在整张表里搜那串原文**，而不是"检查某个字段看起来像哈希"（后者会被"哈希旁边又存了一份原文"骗过）。
- [x] 连续 N 次失败登录后账号锁定，且有测试——**用 EF 存储验的**，见下。
- [x] 登录响应无法区分用户是否存在（有测试**逐字**对比两种错误码与文案）。
- [~] 令牌撤销后旧 access token 立即失效——**移交给票据 11**：它要求的是"撤销"这个机制，而机制（版本号失效 + 请求过滤器）正是 11 的内容。本票交付的是**签发与轮换**，撤销的落点不属于它。

**不知道口令就看不到锁定**、用户名格式非法也不单独报、成功登录清零。

### 实现时发现的一处真实设计碰撞

**分发器只在处理器成功时保存**（`Sender`），而"登录失败"本身就是一次状态变更：
失败计数加一、够阈值就锁定。处理器若不自已保存，**锁定永远不会生效**——
每次失败都被安静地丢掉，接口照常返回"用户名或密码错误"。
那是一个**看起来在防护、实际没有**的实现，而且所有测试都会通过。

所以处理器显式 `IUnitOfWork.SaveChangesAsync()`——仍在分发器开的事务里，
"一个命令一个事务"没有被破坏，只是"提交"由处理器自己发起。

**这也解释了为什么这组测试必须用 EF 存储**：内存存储保存的是聚合实例本身、改动立刻可见，
那个缺陷在它下面根本不存在，因而也验不出来。

### 两个安全设计点

**① 顺序：先验口令，再报"锁定/禁用"。** 如果"已锁定"先于口令校验返回，
攻击者提交任意口令就能判断账号存在——那样"两种错误一致"的防护就白做了。
所以锁定只在口令正确之后才说：那时对方已经证明他是账号主人，告诉他有意义；
而不知道口令的人无论账号存不存在，看到的都一样。

**② 用户不存在时也做一次哈希校验。** 否则"不存在"会明显更快——
那是一个**计时侧信道**，几万次请求的耗时统计足以把用户名枚举出来。

### 还差什么：**形态决定**

票据开头那三个选项（A 自研 JWT / B OpenIddict / C 外部 IdP）**必须先定**：
- refresh token 的轮换与哈希存储是 A/B 的事；选 C 则由 IdP 拥有，做了是白做。
- 撤销立即生效（验收 5）依赖票据 11 的版本号机制，而它的落点也随形态变化。

**与形态无关的部分已经做完**，所以这个决定不再是"开工前的门槛"，
而是"最后三分之一的岔路口"。

#### 一处必须说清的设计决定：为什么不用 `IPasswordHasher`

刷新令牌的哈希**必须确定性**——因为刷新时要**按哈希把它查回来**。
而口令哈希每次加随机盐、故意慢 21 万次迭代；用它存刷新令牌，**第二次刷新就再也查不到它了**。

刷新令牌原文有 256 位熵，不需要慢哈希抗爆破；SHA-256 在这里只有一个作用：**让库里不出现原文**。

#### 重放按被盗处理

分不出"客户端重试"与"令牌被偷"，所以按坏的那种：**撤销该用户的全部刷新令牌**。
丢掉一次"客户端重试"，换掉一次"攻击者一直能用"。

#### 本轮踩到的三个坑

**① 测试的作用域形状与宿主不一致。** 第一版整个用例只建一个 DI 作用域，于是
`IdentityDbContext` 被两条命令共用，处理器从**变更跟踪器**里读到了上一条命令缓存的实体——
"被禁用的账号还能刷新"这条测试因此**假通过**。真实宿主每个请求一个作用域。
修法是 `IdentityTestHost.InScopeAsync`。

**② `ValidateOnBuild` 又抓了一次漏改。** 给 `LoginHandler` 加了 `IAccessTokenIssuer` 依赖之后，
三个测试类里只改了一个——另外两个立刻红，因为**那两处容器组装不出应用**。
修法是把组装抽成 `IdentityTestHost.Build`，**只写一遍**。

**③ 配置在注册时被读死。** `AddIdentityJwtIssuer` 第一版在注册那一刻就
`GetSection("Jwt").Get<JwtOptions>()`——于是**任何之后才加上去的配置源都读不到**
（测试的 `ConfigureAppConfiguration`、宿主的 AgileConfig 都是）。
结果是签发拿到空密钥、每次登录 400，而且失败点离原因很远。
改成 **`AddOptions().Bind().ValidateOnStart()`**：绑定发生在启动那一刻（两边配置源都在），
而"密钥不合格"从"第一次登录"提前到**进程启动**。

**密钥不进仓库**：生成 48 字节随机值写进 `env/platform.dev`（已 gitignore、也被模板排除），
实测模板产物里出现次数为 **0**。
