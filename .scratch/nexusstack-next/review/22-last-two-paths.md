## 一、先说我自己的错：一个假阴性

写完调度那一段，第一次跑出来是：

```
5. 一个节拍后查任务    → 200  已被触发=False
```

而同一轮的日志里明明写着：

```
[15:00:31 INF] [7] [] 调度一轮：检查 1 个，触发 1 个，跳过 0 个。
```

条目里也明明白白有 `"lastRunAt":"2026-09-30T07:00:31..."`。

**是我找错了字段**——断言里找的是 `executionCount`，而响应的形状里根本没有那个字段。
"没找到"于是被读成了"没触发"。

> 这是本会话**第三次**同一类事故：
> 第 23 轮"没匹配到输出"被读成"没有结果"；第 28 轮"403"被读成"权限正确"；
> 这一次"字段名写错"被读成"功能没工作"。
>
> 三次的形状完全一样：**一个失败的观测，被我当成了一个关于世界的结论。**

已修（判据改成 `lastRunAt`）。**Scheduling 的触发链路是通的**——而且这条现在有了真实 HTTP 的证据。

## 二、Platform 的写路径经边缘打不通

```
1. 经网关读设置        → 200（公开）
2. 经网关写设置        → 405     ← 期望 204
   直连后端写（对照）  → 204     ← 端点本身是好的
3. 写后读回            → 200  {"key":"journey.key","value":null,...}   ← 写根本没发生
```

**405 是网关给的**：路由表里 platform 只有一条 `platform-read`，写死了 `methods: ["GET"]`。

于是我上一轮加的那条检查**是绿的**——因为它只看**前缀**，而 `/api/platform/...` 确实有路由。

> **"前缀有路由"和"这个端点打得通"是两件事。** 前者便宜好查，后者才是用户要的。

这和上一轮的 Auditing 是同一类（"有意只读"与"忘了配路由"从外面看一样），
但**更隐蔽一层**：它的前缀是有路由的。

### 处理：立票 68，并把检查细化到方法

`Platform` 是配置的**唯一真相**，而现在**没有任何路径能改一条设置**——
没有种子、没有别的写入者、边缘也只有读。于是"唯一真相"是**只读的真相**，
而**不会有任何东西报错**：读得到（200）、写被拒（405），两者都像正常状态。

**该不该经边缘改设置是一个产品决策**（加路由 / 登记为内部 / 干脆删掉这两个端点），
所以立了票据 68，`needs-info`。

## 三、把检查细化到"方法 + 路径"

上一轮那条只看前缀的检查**已被删掉**（方法级版严格涵盖它），
新的 `EveryModuleEndpointIsRoutedOrDeclaredInternalTests` 做四件事：

1. 从每个模块里解析 `MapGroup` 前缀与每个 `MapVerb` 的路径，拼成完整路径；
2. 对每个 `(方法, 路径)`，找一条**覆盖**它的路由；
3. 覆盖的判据照着 YARP 的形状：**第一个 `{` 之前是基；基以 `/` 结尾才是前缀匹配**，
   否则只匹配它自己——`/api/identity`（无斜杠）**不覆盖** `/api/identity/login`；
4. 没覆盖的，必须在 `DeclaredInternal` 里（方法可以写 `*`）。

反向验证：拿掉 `("PUT", "/api/platform/settings")` 那条声明 →

```
[FAIL] PlatformModule：PUT /api/platform/settings/{key}
```

**正是那个缺口，点名到端点。**

### 两条检查的分工，写清楚免得下次又搞混
