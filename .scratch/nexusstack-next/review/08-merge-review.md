# 08 — 合并之后再查一遍：我自己的改动

**日期**：2026-09-29
**范围**：`src/Hosts/`、五个模块、`src/Gateway/.../routes.json`、相关文档
**方法**：**专门针对我刚做的那次合并**——一个回合内把五个服务并成一个，
所以这次按"最不信任自己"的方式查，而不是复述我上一轮的结论。

---

## 结论先说

**合并本身是好的**：端点一条没丢、跨上下文引用仍为零、边缘策略逐条不变。
但查出 **6 条问题**，其中 **2 条是真的静默失效**，另有一条是**我自己的验证不可重现**。

---

## 一、先验证"我没弄丢什么"

| 检查 | 结果 |
|---|---|
| 端点清单 | OpenAPI **20 条路径**，与五个模块源码逐条对得上 |
| 跨上下文引用 | **0** |
| 架构不变量测试 | 11/11（合并前 10 条，**没有一条被改**） |
| 边缘策略 | 公开 200 / 需认证 401，逐条实测一致 |

20 条路径的构成（Files 的 `/{id}` 与 Platform 的 `/{key}` 各自合并了多个方法，
所以路径数少于操作数）：Identity 8、Platform 2、Scheduling 4、Auditing 2、Files 4。

**没有端点丢失。** 这是我上一轮**没能证明**的（当时只报了"20 条路径"，却不知道本该是多少）。

## 二、【静默失效】模块漏接

合并带来的**新失效模式**：加一个模块却忘了在宿主里 `Map<Ctx>Endpoints()`，
它的端点是**静默消失**的——编译通过、测试通过、启动正常，只是路由表里少了几条。

**这与本项目反复出现的形态完全一致**：一个不受检查的声明会腐烂。

**修法**：新架构测试 `EveryServiceModule_IsWiredIntoAHost`——
枚举 `src/Services/*`，断言宿主的 `Program.cs` 里同时出现 `Add<Ctx>Module` 与 `Map<Ctx>Endpoints`。

**反向验证**：删掉 `MapFilesEndpoints()` 与 `MapAuditingEndpoints()` → **精确变红**；还原 → 11/11。

**它的诚实边界**：这是**文本级**检查，比运行时验证弱一档。
它能抓住"漏了一行"，抓不住"调用写错了"。但那正是最现实的失误。

## 三、【真的问题】Files 的存储故障走两条路，而我只说了一条

我上一轮声称"Files 查存储是否可写可删"。实测后发现**不完整**：

| 故障 | 实际表现 |
|---|---|
| **启动期**路径不可创建 | **进程直接崩**（`DirectoryNotFoundException`），就绪检查根本来不及报 |
| **运行期**存储掉线 | 就绪检查报 **503**，`live` 仍 200 ✓ |

两条路都验证了：

```
正常运行              -> ready 200
删掉存储目录（运行期）  -> ready 503, live 200   ← 检查确实在跑
StorageRoot 指向 Z:\  -> 进程崩溃（没有 HTTP 可答）
```

**两者互补，不是重复**：启动期的快速失败是对的（配置错就该起不来），
运行期的降级由就绪检查兜住。`AGENTS.md` 已把这两条分开写清楚。

**顺带发现一处设计问题**：`AddFilesLocalDiskStorage` 在 **DI 注册期**就
`Directory.CreateDirectory`。**注册期做 I/O 本身就不该**——
它让"注册服务"这个纯内存动作可能抛异常，而且异常发生在容器构建之外，
排查时看到的是一句 `Unhandled exception` 而不是"配置错误"。

## 四、【我自己的验证不可重现】

上一轮 SignalR 的端到端验证（真客户端、两条推送、只在变化时推）
是在 `%TEMP%` 的临时探针里做的——**仓库里没有任何东西守着那个 hub**。

验证是真的，输出是真的，但**它不可重现**：下次有人改坏 hub，跑 `dotnet test` 不会红。

`Microsoft.AspNetCore.SignalR.Client` 的中央包声明因此无人使用（我已删掉它，
以及同样无人使用的 `Mvc.Testing`）。**删除是对的**——留着一条没人用的声明，
只会让中央包管理看起来比实际用得多。但缺口要记下来，见票据 52。

## 六、【命名】两处，都是自己记过的

## 这份评审与 07 的关系

07 查的是"**我设计的东西有没有做错**"；08 查的是"**我刚改的东西有没有改坏**"。

两者都有一个共同结论：**最危险的不是错误本身，是"没有东西会响"的错误。**

除非有人专门为它们写一条。
