# 评审 20 —— 授权链的第一环是断的（第 28 轮）

上一轮把端到端旅程修通了，走到第 3 步停在 **403**：

```
3. 带令牌经网关        → 403   ✅ 已认证但无该权限，fail-closed 正确
```

我把它读成"新用户本来就没权限"——**然后停在那里**。

这一轮往下问了一句：**那权限从哪儿来？**

## 发现：**没有用户能拿到任何权限**

顺着授权链一环一环查：

| 环节 | 状态 |
|---|---|
| 创建**菜单** | ❌ **没有用例，也没有端点**。`MenuTree.AddRoot` 在领域层存在，**没有任何地方调用它** |
| 创建 api-resource | ✅ 有 |
| 把 api-resource 挂到菜单 | ❌ 做不到——没有菜单可挂 |
| 角色授予菜单 | ✅ 用例有——但没有菜单 ID 可传 |
| **内置根账号** | ❌ **没有任何种子/引导逻辑**；`User.Create` 的 `isBuiltIn` 永远是 `false` |

Identity 的**全部**用例：

```
CreateUser  AssignRole  GetUserPermissions  CreateRole  GrantMenuToRole
CreateApiResource  Authorize  Login  Logout  RefreshToken
```

**没有 `CreateMenu`。**

于是：菜单建不出来 ⇒ api-resource 挂不上 ⇒ 角色授不到菜单 ⇒ **权限集合永远为空** ⇒
**所有受权限保护的端点永远 403**；而没有根账号 ⇒ `IsRoot` 那条旁路**不可达**。

## 为什么之前没人发现

**三层的绿都在，而它们各自都没走到那条路：**

- **单元测试**直接构造聚合，绕过了"**能不能建出那个聚合**"；
- **集成测试**用 `WebApplicationFactory` 直打宿主，验的是 401/403/404 这类边界，
  **没有一条走到过"授予权限之后 200"**；
- **端到端旅程**刚修好，而它走到 403 就停了——**我把"失败"读成了"正确"**。

> 这正是评审 19 那条教训的另一半：
> **只走到 403 就停，等于只验了失败路径。**
>
> 一条 403 有两种含义：「正确地拒绝了没有权限的人」与「**没有任何人可能有权限**」。
> 它们的观测值一模一样，而**只有往下走一步才分得开**。

## 处理：立票，不擅自修

这不是一个能在 review 里顺手补的洞——它要两个**产品决策**：

1. **第一个根账号从哪儿来？**（启动播种 / 一次性 CLI / 首个注册者即根——三条路代价不同）
2. **菜单从哪儿来？**（加菜单管理端点 / 随部署导入种子数据 / 干脆去掉菜单这一层）

所以立了**票据 67**，标 `needs-info`，把证据链、两条决策的代价、以及验收标准都写在里面。

**review 的职责是把问题定位到"只需要做一个决定"的程度，而不是替用户做那个决定。**

## 一条值得单独记的观察

`AccessPolicy.Decide` 里 **`IsRoot` 的旁路是有测试的**（`PermissionKey_RootBypassesTheKeyLookup`），
`Role` 的授予/撤销有测试，`UserPermissionReader` 的缓存失效有测试——
**每一环都是真的、都测过，而整条链子走不通。**

> 一条链子的强度，不取决于每一环有多结实，而取决于**有没有人从头到尾走过一次**。
