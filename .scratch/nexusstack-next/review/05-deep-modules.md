# 05 — 用深模块的尺子量自己

**日期**：2026-09-29
**尺子**：`codebase-design`（模块 / 接口 / 深度 / 缝 / 适配器）
**范围**：`NexusStackNext` 全部 `src/`

前四份 review 量的是**参照仓库**。这一份量自己。

## 结论先说

**大的地方是深的。风险不在大模块，而在"缝的声明先于适配器"。**

## 一、深模块：数据与判断

| 模块 | 实现规模 | 接口 | 删除测试 |
|---|---|---|---|
| `Sender`（应用层分发器） | 259 行 | `ISender` 3 个方法 | **挣饭钱** |
| `GatewayRouteTable` | 230 行 | `Create` / `FromJson` / `ToJson` | **挣饭钱** |
| `MenuTree` | 304 行 | 聚合方法 | **挣饭钱** |
| `IOutboxStore` | 待 EF 适配器 | 4 个方法 | 刻意深 |

**`Sender` —— 259 行藏在 3 个方法后面。** 删除测试：删掉它，每个调用方都要自己解析处理器、
自己处理"找不到处理器"、自己决定校验管线跑不跑、自己管事务边界。
复杂度会在 N 个调用方那里重新出现。它是深的。

**`IOutboxStore` —— 4 个方法，而且刻意没有 `Add`。** 注释里给了理由：
写入是聚合持久化的一部分（拦截器在 `SaveChanges` 时收集领域事件并落 Outbox），
不是投递器的职责；给投递器一个"写"的口子会让"同事务"这条保证变得可疑。

这是深模块原则的一次正确应用：**把能力切成两半、各给一个接口，
比给一个大接口再靠约定约束调用方要深。**

## 二、缝的清单与被验证的程度

| 缝 | 生产适配器 | 测试替身 | 判定 |
|---|---|---|---|
| `IIdGenerator` | 1（Snowflake） | 0 | 真缝 |
| `IClock` | 1（系统时钟） | 3 | 真缝（时间必须能固定） |
| `IRouteTableStore` | 1（文件） | 0 | 真缝（多副本时换实现） |
| `IScheduledTaskStore` | 1（内存） + 待 EF | 1 | 真缝 |
| `IOutboxStore` / `IInboxStore` / `IEventBus` | **0** + 待 EF/RabbitMQ | 1 | **声明先于适配器** |
| `IFileStore` / `IFileUrlProvider` | **0** + 待本地磁盘/对象存储 | 0 | **声明先于适配器** |
| `IUnitOfWork` / `IRequestValidator` | **0** + 待 EF | 1 | **声明先于适配器** |

## 三、`IFileUrlProvider` 看着像多余的缝，其实不是

单看"一个只有 1 个方法、零适配器的接口"，它是"假设的缝"的典型嫌疑。
但代码里的理由站得住：

> 只有能给出可访问 URL 的存储（对象存储）才实现它；本地磁盘存储不实现，
> 调用方因此不会误用它。**做不到的能力不给接口，就没有"声明了却抛异常"的中间状态。**

参照仓库的 `IFileStorage` 有 14 个成员，而**没有任何一个实现支持全部成员**——
`AliyunFileStorage.GetAbsolutePath` 抛 `NotImplementedException`，偏偏视频上传路径会调到它，
于是那条路一上传就崩。

所以这道缝上**确实有东西变化**：本地磁盘存储与对象存储是具名的一对适配器。
它满足"两个适配器才是真的缝"，只是那两个都还没写。

## 四、真正的问题

**没有一道缝被真实适配器检验过。**

这正是深模块那套规则真正警告的事：接口的形状应该由**缝上真实变化的东西**塑造，
而不是由想象中的实现者塑造。现在 `IOutboxStore` 的 4 个方法、`IFileStore` 的 3 个方法，
都是照着"EF Core 大概会这么写"设计的。等 EF 适配器真的落地时，
如果它需要 `ReadPendingAsync` 之外的东西（比如"批量抢占"以避免多实例重复投递），
接口就得改——而那时改动会波及已有的测试替身与调用点。

**这是已知且已被记录的赌注**，不是疏忽：ADR-0002 与 ADR-0004 明确写了
EF Core 与 RabbitMQ 是计划的适配器，而它们阻塞在测试库与 broker 上。
缓解措施恰好是深模块规则的另一条：**接口就是测试面**——
测试替身跨的是与将来真实适配器**同一道缝**，因此接口至少被"跨过"过。

**已经做掉的那半**：给最可疑的一道缝写了**第二个适配器**，语义刻意与第一个不同——
`tests/Contexts.Tests/FileStoreSeamTests.cs` 里，"本地磁盘"（有路径、无 URL 能力）与
"对象存储"（键带前缀、能签发有期限链接）跑**同一组契约断言**，
而 `IFileStore` 三个方法一个都不用改。

结论：**这道缝是直的。** 两边都能满足而不需要接口弯曲。
另外三条断言把缝的存在理由钉住了——只有对象存储声明 `IFileUrlProvider`，
而那条断言还顺带被编译器证明了一次：直接在具体类型上写 `is IFileUrlProvider`，
编译器算出它是常量并报 **CS0184**。编译器自己说这两者毫无关系。

**还没做的那半**：其余几道缝（`IOutboxStore` / `IInboxStore` / `IEventBus`）
的第二个适配器需要 EF Core 与 RabbitMQ，阻塞在测试库与 broker 上。
在那之前，它们的形状仍属**未验证**——这是本评审留下的最大一条。

## 五、用语偏差

审计 `src/` 的注释与文档，混用情况：

- **`边界` 出现过 4 次**。其中属于 DDD 的"限界上下文"是对的（那是术语）；
  凡是用来指"模块边界"的都该改成**缝**。
- **`服务` 出现 14 次**。指可部署的微服务时是对的（那是本项目的实体）；
  用来指"模块"时不对。
- `组件` 1 次，应改成**模块**。
- `component` / `boundary` 各 0 次（英文写得好）。

用语本身不改变代码，但它决定讨论的分辨率。已把规范固化成
`docs/agents/design-vocabulary.md`，并在 `AGENTS.md` 里引用。

## 六、这份 review 没有推翻什么

八条架构不变量与深模块原则**没有冲突**，而且有几条本来就是同一件事的两种说法：

- 不变量 7（"共享代码要被第二个消费者证明需要，才允许上移"）
  ≈ "一个适配器只是假设的缝，两个才是真的缝"。
- 不变量 8（"每个宿主显式组装自己"）≈ 把组装留在**接口之外**，不进实现的肚子里。
