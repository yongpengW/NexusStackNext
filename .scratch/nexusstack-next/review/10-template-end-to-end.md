# 评审 10 —— 模板端到端（第 18 轮）

评审 09 看的是"**文档声称的**"与"**代码实际做的**"之间的差。
这一遍换一个完全不同的角度：**交付物本身**。

这个仓库的交付物**是模板**。所以"它作为一个模板好不好用"不是附加题，而是主问题——
而它整场都没被完整验过一次。

## 验证方式

装模板、生成一个新项目、**在生成物里**做各种事。

```
dotnet new install <repo> --debug:custom-hive <hive>
dotnet new nexusstack-next -n R18Check -o <out> --debug:custom-hive <hive>
```

## 发现 1（真实缺陷）：`check-tracker.ps1` **硬编码了本仓的 effort 名**

```powershell
$scratch = Join-Path $repoRoot '.scratch/nexusstack-next'
```

它对**本仓库**是对的。但这个脚本**跟着模板一起分发出去了**，而别人的 effort 会叫别的名字。

于是新使用者的体验是：

```
跟踪器检查无法执行——以下路径不存在：
  [票据目录] <out>\.scratch\nexusstack-next\issues
```

**那句话把他指向一个他不该有的目录**——他会以为脚本坏了，或者以为必须先建一个叫
`nexusstack-next` 的目录。而真实情况是"你该建自己的 effort"。

### 修法

自动发现 `-Effort`：`.scratch/` 下**恰好一个**目录就用它；
**多个**就列出来并要求显式指定（不猜）；**没有**就退回原来的"路径不存在"提示。

### 验证（在生成物里改名成 `my-feature`）

| | 用户看到的话 |
|---|---|
| 改之前 | "路径不存在 `.scratch/nexusstack-next/issues`" —— 指向一个错误的目录 |
| 改之后 | "在 `…\my-feature\issues` 下**一张票据都没找到**——检查等于没跑，不能当作通过" |

**改之后那句话是真的**：effort 存在、但里面是空的。这才是使用者需要知道的事。

## 发现 2（我自己引入的回归）：README 里一条**死引用**

第 16 轮我往 README 里写了：

```
> 第 16 轮 review 发现并修好了（见 `.scratch/nexusstack-next/review/09`）。
```

而模板**排除** `.scratch/` —— 所以那句话在**每一个生成物**里都指向一个不存在的路径。

改成通用表述。**记在这里是因为它是我自己的手笔，而且是同一天加的**：
写文档时引用"本仓的某个文件"很自然，但**文档是要发出去的东西**，
每一条路径都要问一句"它在生成物里存在吗"。

## 发现 3（判断后**不改**）：生成物里的 `check-tracker.ps1` 会失败

它在空项目里**必然失败**，因为没有任何票据可查。而**那是对的**：

> 检查没有对象可查时不得报告通过。

一个"没有东西可查"就报绿的检查，与一个不会失败的检查是同一件事。
所以它的失败是**正确的行为**，不改。

## 发现 4（判断后**不改**）：满篇的「票据 NN」「评审 0N」

生成物里有二十多处引用本仓的票据编号与评审编号。它们对使用者**打不开**，
但每一条的**理由都写在同一个注释里**——票据编号只是出处，不是论据。

判断是**保留**：它们记录的是"这个决定是被什么逼出来的"，
而删掉之后读者会以为那些设计是凭空想出来的。真正要防的是"**只有**编号没有理由"——
而那一条已经在写作规范里了。
