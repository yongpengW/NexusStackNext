# 评审 21 —— 没人走过的另外三条路（第 29 轮）

上一轮的教训是"只走到失败就停会漏掉整条链"。这一轮去找**还有哪些路没人从头走过**：

| 路径 | 之前的证据层级 |
|---|---|
| Files 上传下载 | 单元级 |
| Auditing 落库 | 单元级 |
| Scheduling 触发 | 单元级 |

方法还是真实 HTTP —— 起两个真进程，走网关。

## Files：**全通**（一条阴性结果，也是结果）

给旅程加了 Files 那一段，并且**比的是哈希不是状态码**——
"上传成功、下载回来却是别的内容"这种实现状态码全绿，而用户拿到的是错的文件。

```
5a. 经网关上传文件      → 201
5b. 取元数据            → 200
5c. 下载文件            → 200  字节一致=True
5d. 删除文件            → 204
5e. 删后再取元数据      → 404（期望 404）
```

**字节往返一致**，删除后元数据消失。这条链是结实的。

（顺带确认了一件事：上传端点取的是**原始 body + `name` 查询参数**，不是 multipart，
所以没有 minimal API 的防伪令牌问题——这一点读代码时不容易确定，跑一次就确定了。）

## Auditing：**经边缘不可达，而这件事没有写下来**

顺手核了一遍"网关的路由表覆不覆盖五个模块"：

```
Auditing     /api/auditing   ❌ 经边缘不可达
Files        /api/files      ✅
Identity     /api/identity   ✅
Platform     /api/platform   ✅
Scheduling   /api/scheduling ✅
```

**只有 Auditing 没有路由。**

### 而它的 ADR 自相矛盾

Auditing 的 ADR 正文写着（在解释 `GET /api/auditing/entries` 为什么返回 405）：

> 那条路径上现在有写入口（`POST`），所以框架的回答是"这条路不通"而不是"没有这条路"。

而它的 `## Consequences` 写着：

> **事件进入是唯一的写入路径。**

**两条不可能同时为真**——`POST /api/auditing/entries` 自己就是一条写入路径。
（而它引以为据的"事件进入"这条路径**还没建**：事件总线与发件箱就绪，但没有生产者。）

### 已更正，并把"有意"变成可检查的声明

ADR 里补了一张表：两条写入路径各自的**状态**与**谁能用**；
并写明 `POST /api/auditing/entries` **经边缘不可达是有意的**（进程内 / 运维用）。

> **"没写下来"与"忘了配路由"，从外面看是一样的。**
> 两种情况的观测值都是 404，两种情况都不会有任何东西报错。

## 把这条变成检查

新增 `EveryModulePrefixIsReachableOrDeclaredInternalTests`：

> 每个模块的 `/api/<前缀>` 要么在网关有路由，要么出现在一份**显式的"内部"清单**里。
> 两样都不占就红，而失败信息告诉写的人**两个选项**。

反向验证（**先确认编译通过**——这条纪律第五次生效）：

```
步骤 1：✅ 编译通过
步骤 2：[FAIL] EveryModulePrefix_IsRoutedOrDeclaredInternal
  下列模块的前缀经边缘不可达，而且没有声明这是有意的——路由漏配与有意内部从外面看是一样的：
    AuditingModule：/api/auditing（既没有网关路由，也没有登记为内部）
步骤 3：还原 → 绿
```

**新加一个模块却忘了配路由时，会被点名。**

## 这一轮的账

| | |
|---|---|
| 核实为**结实** | Files 的完整 HTTP 链路（含字节往返） |
| 发现并修复 | Auditing 的 ADR 自相矛盾 + "经边缘不可达"没被写下来 |
| 新增防线 | 模块前缀必须有归宿（路由或显式内部） |
| 顺带 | 端到端旅程多了 Files 一段 |

## 还剩哪条路没人走过

- **Scheduling**：`SchedulingWorker` 有真 `PeriodicTimer`，但它**触发之后发生什么**没有端到端证据。
- **Platform**：设置的读写被 Files 的旅程顺带覆盖了一半（同一个宿主），但没有独立的旅程。
