# Identity 查询开销实测

票据 [137](https://github.com/yongpengW/NexusStackNext/issues/137)，基线 dev `567346f`。
2026-10-08 继续本机开发；整体 NS/PoS 能力目标仍暂停。本轮增加测量与回归，产品实现没有改变。

## 边界与复现

`IdentityQueryJourneyTests` 使用公开 ISender 命令/查询，以及真实网关进程 → Kestrel 平台宿主的 HTTP。
每个 ISender 调用创建独立 DI 作用域；每个测试从冻结空结构复制独立临时库，沿用共用测试 PostgreSQL、
单所有者与建库/迁移/删库单许可。测试账号、角色与资源只属于该例。
配置由被忽略的 `env/test.dev` 注入，连接配置和原始报告不入库。

```powershell
dotnet build NexusStackNext.slnx -c Release
pwsh -File scripts/run-tests.ps1 -Scope Focused -Project HostIntegration.Tests -Filter 'FullyQualifiedName~IdentityQueryJourneyTests' -Configuration Release -NoBuild
```

权限空集合先冷后热；授予菜单、提交 API 资源后再次冷/热读取；再提交新的 API 资源，登录并经网关读取受保护菜单。
退出后断言会话版本增加一次，原令牌立刻得到 401。200/401 与权限内容都是行为断言，耗时没有硬阈值。
新类尚未纳入本机显式并行资源声明，使用未审核类的独占回退；已有 169 类的并行声明不改。
它增加一项宿主回归，不删除或改写原测试身份及断言。

## 计时含义

仅按本次 Activity trace 观察 `IdentityDbContext` 和 `OperationJournalDbContext`；后台其他 trace 不计入。
输出只含固定阶段、次数和毫秒，不读取或输出 SQL 文本、参数、请求/响应载荷、身份和连接配置。
`commands/sql_ms` 是 Identity 的 EF 命令执行次数与诊断耗时；一次 DbCommand 可包含多条语句，
不把该次数冒充服务器全部语句数。`connections/connection_ms` 是 Identity 的 EF 打开连接诊断，
不是 PostgreSQL 全局连接数，也不是所有物理建连次数。建库、模板迁移、宿主启动、登录和命令提交位于测量之外。
首次查询总时间仍包含该路径的 JIT、查询编译、装载等冷成本。

HTTP `total_ms` 截止客户端收到完整响应；另等待最多 10 秒，确认平台服务端请求 Activity 已结束，
从而涵盖可能晚于响应的 Finished 日志落盘。`server_ms` 是平台请求管线时间，
不包含网关进程的内部计时。平台请求结束依据 [ASP.NET Core 的请求 Activity 生命周期](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Hosting/Hosting/src/Internal/HostingApplicationDiagnostics.cs)。
`journal_commands/journal_sql_ms` 单列平台来源日志的 EF 命令；`journal_transactions/journal_transaction_ms`
仅计 BEGIN 与 COMMIT 诊断，不是整个事务存续时间。网关本例使用 Memory journal，不能据此推断生产网关持久日志成本。
这些时间属于嵌套或不同边界，不能全部相加，也不能用总时间减 SQL 就认定为连接池等待。

## 两轮同边界结果

两轮均使用同一实现和共用服务，全部行为断言通过；运行前只读探测分别为 2/100、2/100 个连接，
其他活动连接为 0。运行正常返回后所有权为 `idle`。没有重跑完整本机宿主，不能据此更新它的总墙钟。
原始 TRX 位于本机临时目录 `nsn-query137-final-round1` / `nsn-query137-final-round2`，不提交原始诊断。

| 空权限冷读 | 2 | 203.0 / 184.1 | 56.4 / 54.8 |
| 空权限热读 | 0 | 0.9 / 4.1 | 0 / 0 |

这些阶段 Identity 连接获取累计 0–0.3 ms；热读根本没有打开数据库连接。

## 可证伪假设与改良方向

1. **平台来源日志同步写入是显著请求成本。** 两轮所有 HTTP 阶段都出现 12 次日志命令，
   日志 SQL 约 280–291 ms；源码 `EfOperationJournal.AppendAsync` 的 Started/Finished 各六次命令吻合。
   改良优先评估合并幂等检查与数据库命令往返，而非增加权限缓存。验证必须保留消息/阶段幂等冲突、
   容量竞争、事务独立、失败降级、Started/Finished 和即时权限拒绝，按相同网关旅程先后对照。
   本票没有修改该一致性协议；尚未证明某个新实现能安全节省多少时间。
2. **权限冷读的分次装载有成本。** 授权后冷读三次 Identity 命令，热读为零，HTTP 冷/热差三次；
   当前用户 → 角色 → API 资源的装载可作为只读投影候选。两个冷请求还含路径冷启动，
   不能把全部冷/热总差算成 SQL 收益。先测业务缓存命中率与结果规模，再决定是否值得新增投影端口。
3. **连接池排队是当前瓶颈。** 本轮不支持：Identity 打开连接累计至多 0.3 ms，
   明显小于 SQL 时间。但准备已预热连接且环境安静，本测量不排除生产峰值、池耗尽或物理建连故障。
4. **热 HTTP 重复做权限 SQL 查询。** 本轮不支持：热请求两条 Identity 命令，
   分别对应会话权威读取及菜单业务读取；退出后拒绝只剩会话读取。
   网关自身验签并转发，权限缓存命中后不读权限源。不能为了省这一次会话读取而跨请求缓存权威状态，
   否则本例的即时退出拒绝可能失效。

本轮结论是已有权限热缓存有效，下一项值得专项验证的是来源日志往返；没有证据支持放大连接池或削弱会话校验。
本票新增可重复的诊断与真实网关回归，**没有产品提速百分比**。并发负载、生产网关 Postgres journal、
大角色/资源集合、故障/重试成本需要各自的同边界测量，不能由这两轮安静环境代替。

## 来源日志往返改良（#139）

[139](https://github.com/yongpengW/NexusStackNext/issues/139) 以已交付 dev `7bbb725` 为基线，
只重构 PostgreSQL 来源日志追加。消息锁、阶段锁仍依次获取，并绑定原来的独立连接与事务；
使用原生 `NpgsqlBatch` 执行两条锁语句。一次读取同时检查消息 ID 与 Source/OperationId/Phase，
最多命中两条不同记录；只有消息 ID 命中才读取载荷并比较内容。身份冲突仍先于容量拒绝。
条件容量更新、插入和提交保持原事务，Memory、迁移、恢复/清理、取消及失败降级政策不改。
原生批次减少等待服务器回复的次数，不能保证网络层恰好只有一个数据包，依据
[Npgsql 批处理文档](https://www.npgsql.org/doc/basic-usage.html#batching)。

成功追加一条新观察的主体执行由六次命令变成四次：锁批次、联合读取、容量更新、插入。
主体 SQL 语句由六条变成五条，因为锁批次仍含两条语句；BEGIN/COMMIT 各一次另计。
同一请求的 Started/Finished 合计从十二次主体追加命令变成八次。
`SaveChanges` 在已有事务里还保留自动创建/释放保存点，每条观察额外两次命令；
不把四次主体执行声称为日志事务的全部数据库操作。

测试诊断新增 `provider_commands/provider_ms`：按当前 trace 统计 `Npgsql` 的 `postgresql` Activity，
使绕过 EF 的原生锁批次仍被观察。计数包括 Identity 命令、日志 EF 命令、原生批次和保存点创建/释放；
不能把它全部解释为业务查询，也不能当成 PostgreSQL 全局 SQL 数或网络包数。
[固定版本 Npgsql 10.0.3 实现](https://github.com/npgsql/npgsql/blob/v10.0.3/src/Npgsql/NpgsqlCommand.cs)
为整个原生批次启动一次命令 Activity。只请求传播数据，不读取 SQL、参数或标签；
provider 时间与 EF 诊断嵌套，不叠加。Npgsql 的 BEGIN/COMMIT 走内部消息，
没有本探针统计的命令 Activity；它们由 `journal_transactions` 的 EF 事务事件另计。
固定版本 [EF 10.0.12 保存点实现](https://github.com/dotnet/efcore/blob/v10.0.12/src/EFCore.Relational/Storage/RelationalTransaction.cs)
与 [Npgsql 10.0.3 事务实现](https://github.com/npgsql/npgsql/blob/v10.0.3/src/Npgsql/NpgsqlTransaction.cs)
说明两种诊断的差别。每请求多出的四个 provider span 对应两个日志事务的保存点创建/释放，
不是那四个 BEGIN/COMMIT 事件。HTTP 各阶段断言 provider 与 EF 探针均非空，
不把某个私有命令数或毫秒阈值写成产品契约。

使用相同的新增诊断，在原实现及候选各跑两轮同一 ISender/真实网关旅程；
每轮同时执行新增的交叉身份冲突回归，均通过。运行前只读探测为 2/100 连接、其他活动为 0；
运行正常结束释放所有权。原始报告只留本机临时目录 `nsn-journal139-provider-baseline-1/2`
及 `nsn-journal139-candidate-1/2`。每个请求 Identity 命令仍为冷读 5、热读 2、旧令牌拒绝 1；
日志事务操作仍为 4 次。平台日志 EF 命令由 12 降为 6，但还要加两次原生批次，
不能声称日志只有 6 次数据库执行。

| HTTP 阶段 | 客户端 ms，基线两轮 | 客户端 ms，候选两轮 | provider 次数，基线 → 候选 | provider ms，基线两轮 → 候选两轮 |
|---|---:|---:|---:|---:|
| 冷读菜单 200 | 726.1 / 631.4 | 437.0 / 536.8 | 21 → 17 | 575.5 / 484.0 → 312.0 / 403.2 |
| 热读菜单 200 | 572.5 / 471.4 | 304.0 / 385.1 | 18 → 14 | 501.5 / 408.6 → 252.7 / 321.5 |
| 退出后拒绝 401 | 553.6 / 459.0 | 285.0 / 355.7 | 17 → 13 | 481.0 / 396.9 → 233.7 / 295.0 |

两轮平均热请求 522.0 → 344.6 ms，观察到少约 34%；冷读约少 28%、旧令牌拒绝约少 37%。
这是安静共用环境的少量前后样本，环境延迟也在波动，不能把全部时间差归于这四次执行减少，
也不证明完整宿主测试或生产请求固定快这么多。ISender 权限热读仍为零命令，
权威会话读取仍为一次，退出即时拒绝保持。权限冷读投影、生产网关持久日志和并发负载测量尚未实施。

新增公共接口回归覆盖两个不同记录同时命中消息与阶段身份、并发交叉冲突、满额重投及重开不变。
原实现已通过此行为回归，这是保留语义的重构；反向验证把联合身份条件改错，先确认编译成功，
再确认该回归失败，恢复正确条件后重新验证；另关闭 provider 监听，确认 HTTP 非空探针断言失败。
两次变异均在恢复后重新构建并执行受影响验证。没有把原实现描述为功能缺陷。
本机受影响的来源日志持久化/容量/清理/交付/恢复、HTTP 日志/网关降级和查询旅程共 83 项全部通过，
已声明类沿原四路调度，未审核查询类独占；没有压力停止信号，正常返回后所有权为 `idle`。
不以定向报告代替完整 Linux 23 工程 1938 项验收（保留原 1937 项身份，新增交叉身份回归一项）。
