# 设计用语

本仓库用一套**固定的词**谈设计。词用对了，讨论才有分辨率；混用同义词会让
"这里到底该放什么"变成各说各话。

这套用语来自 `codebase-design`（深模块）。它是**设计**词表（代码结构）；
`CONTEXT.md` 是**领域**词表（业务概念）。两者不要混。

## 词表

**模块（Module）** —— 任何有接口和实现的东西。**刻意与尺度无关**：可以是一个函数、一个类、
一个包，也可以是一条跨层的切片。
*不要用*：单元、组件、服务。

**接口（Interface）** —— 调用方为了正确使用这个模块所必须知道的**全部事实**：
类型签名，但同样包括不变量、顺序约束、错误模式、必需配置、性能特征。
*不要用*：API、签名（太窄，只指类型层面那点表面）。

**实现（Implementation）** —— 模块内部的那堆代码。
与**适配器**区分：一个东西可以是"小适配器 + 大实现"（Postgres 仓储），
也可以是"大适配器 + 小实现"（内存假件）。谈缝的时候说适配器，其余时候说实现。

**深度（Depth）** —— 接口处的**杠杆**：调用方（或测试）每学一单位接口，能撬动多少行为。
大量行为藏在小接口后面 = **深**；接口复杂度和实现差不多 = **浅**。

**缝（Seam）** —— 可以在此处改变行为而**不必改动此处代码**的地方；也就是接口所在的位置。
"缝放哪儿"是一个独立的设计决定，与"缝后面放什么"不同。
*不要用*：边界（与 DDD 的限界上下文撞车）。

**适配器（Adapter）** —— 在某个缝上满足某个接口的具体东西。它描述**角色**（填哪个槽），
不描述实质。

**杠杆（Leverage）** —— 深度给调用方的东西：每学一单位接口换来的能力。
**局部性（Locality）** —— 深度给维护者的东西：改动、缺陷、知识、验证都集中在一处，
而不是散到各调用方。

## 三条可直接用的判据

**删除测试。** 想象把这个模块删掉。如果复杂度**消失**了，它就是个直通管道；
如果复杂度**在 N 个调用方那里重新出现**，它就在挣自己的饭钱。

**接口就是测试面。** 调用方和测试跨的是**同一道缝**。
如果你想测到接口**里面**去，多半是这个模块形状不对。

**一个适配器只是假设的缝，两个才是真的缝。** 没有东西在缝上变化，就别开这道缝。

## 在本仓库里怎么用

- 说"这里需要一个接口"之前，先回答：**缝上会变化的是什么？**
  答不出来（或者答案只是"将来可能"），那是一个假设的缝。
- 写 ADR 时用这些词。不要写"我们加了一个服务组件"，写"我们把这道缝放在 X，
  因为缝上变化的是 Y"。
- 区分"端口"与"接口"：本仓库的 `*.Domain` 里那些 `I*Store` / `I*Provider` 是**端口**，
  它们是接口，但强调"由外层实现"。谈结构时说接口，谈依赖方向时说端口。
