# 授权的默认答案是"拒绝"

参照仓库的授权在配置缺失时是 **fail-open** 的：`ApiAuthorizationOptions.cs:21` 默认 `RootOnly`，
而 `RequestAuthorizeFilter.cs:87-111` 在拿不到配置时会把请求放行。
一次配置事故、一次反序列化失败、一次枚举未赋值，结果都是**全站放开**。

决定：授权链路上的每一个"不知道"都落到拒绝。

- `AuthorizationMode.DenyAll = 0`——它就是枚举默认值，因此任何未赋值的路径都是拒绝而不是放行。
- `PermissionKey` 模式下，端点**没有声明**所需权限键时 → 拒绝。公开端点必须走 `Authenticated` 模式
  **显式**表达，不能靠"忘了标注"这种默认放行。
- 权限集合未知（缓存未命中、用户无角色）→ 拒绝。
- 未知的枚举值 → 拒绝。
- 未认证一律 401，与模式无关——不要用 403 掩盖"你还没登录"。

## Considered Options

- **fail-open**：可用性更友好，配置坏了业务还能跑。但"配置坏了"与"全站放开"是同义词，
  而后者不会有人立刻发现——它不报错、不告警，只是悄悄允许了所有人。
- **每个端点显式 opt-in 放行**：更细，但需要额外的"公开端点清单"机制，
  而漏登记一个端点就变成静默不可访问。默认拒绝把漏登记的后果变成一次**响亮的 403**。

## Consequences

- 每个端点都必须显式声明自己的授权模式。少声明一个 ⇒ 那个端点返回 403，
  是可见的、会被人立刻报修的失败——这正是我们想要的方向。
- 根管理员在 `PermissionKey` 模式下绕过权限键查找。它是"能在系统里做任何事"的角色，
  逐条授予没有意义；这一条被显式写进判定里，而不是靠"给它也授满权限"来变相实现。
- 判定是纯函数，因此"默认拒绝"可以被穷举验证（见 `AccessPolicyTests`），
  而不是靠读配置代码来相信它。
