# 所属上下文按事实契约清理已交付副本

## Context

#64 要求业务事实的来源积压、恢复与保留治理。来源 Outbox 不是中央不可变审计事实表，
也不是只装审计消息的表：Costing 的成本结果和 Scheduling 的触发消息与审计事实共存，
交付管理仍通过这些业务记录查询状态。因此不能把通用“清理全部已交付 Outbox”作为本票的实现。

## Decision

每个生产模块在自身装配中声明审计契约名称，维护实现只访问该上下文的 Outbox，并同时要求：
事件名精确匹配、首次发布确认不为空且已超过当前保留期、死信标记为空。
不接受 HTTP 提供事件名、schema 或任意删除条件。其他业务消息、待投递、死信、Inbox 和中央记录不在删除范围内。
发布确认是 broker 接纳证据，不是中央业务接纳证据；中央消费者必须继续依靠稳定消息身份去重。

Identity、Platform、Files、Scheduling、Costing、Pricing 分别使用同一个维护端口，
变化的缝是所属数据库和事实契约，故公共实现放在 BuildingBlocks.Infrastructure，端口放在 Application。
模块仍显式组装自己的实现，中央 Auditing 不连接来源数据库。

PostgreSQL 使用单条语句完成候选选择与删除：按确认时刻/消息身份排序、有界批次、
`FOR UPDATE SKIP LOCKED` 跳过正在操作的行，删除与选择在同一语句事务内生效。
拒绝借用调用方事务或环境事务，使用独立维护作用域；这条路径不调用业务 SaveChanges，
不保存同作用域暂存的业务改动，也不因为删除投递副本产生新业务事实。
取消、锁等待失败或数据库触发器失败不会提交部分删除。连接在提交应答前断开时可能无法得知删除数量，
维护报告失败并在下一轮继续，不把未知结果伪造为已删除数量；重复清理本身安全。

六个来源模型显式登记 `(EventName, DeliveredAt, Id)` 部分索引，条件为已确认且非死信，
随各自独立 EF 迁移发布。普通启动不迁移；清理工作不能替代迁移门禁。

Identity、Platform、Files、Scheduling 的 Memory 模式使用同一端口和维护循环，
在所属业务存储的同一把写锁下选择当前已提交副本并整批移除。Identity 的提交会替换整个字典，
因此维护器在持锁后才取得最新字典，不能在构造时固定旧快照。
等待写锁支持取消；选择完成后、修改之前再检查预算，取消不产生半批删除。
迟到的发布确认或失败若遇到已清理记录，像 PostgreSQL 一样保持无操作，不重建记录或抛缺键异常。
Memory 依然只用于开发测试，不因维护行为一致而获得跨进程持久性。

每个模块的后台循环独立创建作用域，默认每分钟执行一批、最多 500 条、预算 5 秒，
默认保留首次确认后的七天。它不依赖 broker、任务 worker 或业务开关；可以显式关闭。
每轮只做一批，不因积压持续占用数据库。失败只报告固定诊断，不递归写操作日志或输出原始异常。
`auditing-diagnostics` 健康分类报告本模块维护开关、累计失败数和当前降级；下一轮成功恢复当前状态，
累计失败证据保留。默认值不是生产吞吐量或多机容量验收结论。

维护诊断还记录 `cleanupRuns` 与 `deletedCopies`，分别为本进程内成功完成的自动轮次与这些轮次返回的删除数量。
失败/结果未知的轮次不虚构删除数量，手动直接调用端口也不计入后台循环统计。
它们是维护活动诊断，不是来源当前保留数量或永久历史账本；现有 HTTP 健康入口仍只输出组合状态。

配置位于 `<Context>:AuditDelivery:Cleanup`。本次来源副本保留由当前策略计算，
调整配置会影响旧的已确认副本；它与具有固定 `RetainUntil` 承诺的恢复凭据不同。
中央业务事实的保留与归档政策须单独制定，不能由来源清理推导已归档。

## Evidence and remaining work

`CommittedFactCleanupTests` 通过真实 PostgreSQL 验证时间边界、批次、消息类型隔离、Inbox 保留、
行锁跳过、真实表锁等待取消、删除触发器失败及并发唯一删除。
`CommittedFactCleanupHostTests` 验证后台自动维护、独立上下文的迁移与索引、
故障时保留副本并降级、下一轮恢复，以及 Costing/Pricing 模块在关闭任务和 broker 后仍进行维护。
测试的数据库均为独立临时库或专属 schema；没有对共享运行库执行迁移或清理。

`CommittedFactMemoryCleanupTests` 验证当前快照、批次、并发、类型保留和真实写锁等待取消；
`MemoryCommittedFactCleanupTests` 通过四个实际模块验证自动维护/关闭开关、保留边界、停止记录保留、
清理后迟到确认不重建副本、业务版本不变及后台成功统计。PostgreSQL 自动维护测试同时验证这些成功统计。

本切片只完成已确认事实副本的回收。
未确认/死信的容量限制和带控制记录的专门恢复、中央保留归档仍在 #64 范围内，不能据此关闭票据。
业务消息自身的交付历史保留需要各业务模块另行定义，不能搭便车删除。
