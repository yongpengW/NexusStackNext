# 乐观并发的版本号属于领域，而不是 EF 的配置

每个聚合根带一个 `Version`：**新建时为 1，状态每改变一次 +1。**

## 为什么不是 EF 的 `[Timestamp]` / `IsConcurrencyToken`

那是**实现侧**的机制：它要求有一个数据库列，而且只有在用 EF Core 时才存在。两个后果：

1. **领域层表达不出"这个状态是第几版"**——而"你手里那份是旧的"是一句业务事实，
   不是存储细节。
2. **换掉 EF 就没有并发保护了。** 并发正确性不该取决于用哪个 ORM。

## 为什么必须现在做，而不是等接 EF Core 时

`AggregateRoot` 是**九个聚合的基类**。等接 EF 时再加，要改的是基类 + 九个聚合 +
**每一个改变状态的方法**——而那时这些方法已经散到更多地方了。

这条也是这份仓库的一次自我更正：`review/02` 第 349 行把"无并发令牌 → 静默丢更新"
写成了参照仓库的缺陷，而本仓库自己**零处**并发令牌，且它不在票据 42 的"没做什么"清单里。

## 契约

**`Version` 改变，当且仅当可观察状态改变了。**

- 改状态 → 版本 +1
- **空操作 → 版本不变**：`AssignRole` 重复调用、`ChangeValue` 同值写入、`Grant` 已授权、
  `SetContact` 传入相同值、已禁用的账号再次 `Disable`……

**第二条不是细节。** 空操作若自增，乐观并发会在**没有冲突的情况下**误报冲突；
而误报的代价是调用方开始重试、或者干脆忽略冲突——**那时这个机制就废了**，
而且废得很安静：它还在"工作"，只是没人再信它。

## 实现约定

| 场景 | 写法 |
|---|---|
| `Result` 路径改状态 | `return Changed();` / `return Changed(value);` |
| `void` 路径改状态 | `BumpVersion();` |
| 空操作提前返回 | `return Result.Success();`（**不带** `Changed`） |

这样读代码的人不需要记住每个方法的语义：**末尾是 `Changed()` 就是改了，是 `Result.Success()` 就是没改。**

## 代价（说清楚）

**编译器管不了这件事。** 忘记自增不会有任何报错，只会让并发保护在那个聚合上失效。

缓解措施是测试：每个聚合都有一条"改状态 +1 / 空操作不变"的测试。
这是本仓库里少数几个**只能靠测试而不是靠类型**守住的契约之一——
与"空操作不发事件"是同一类东西，所以两者放在一起测。

## 后果

- 接 EF Core 时，`Version` 直接映射成并发令牌列（`IsConcurrencyToken`），不需要改领域。
- 应用层将来可以用它做 If-Match / 409 冲突响应。
- 不可变聚合（`ApiResource`、`AuditEntry`）永远停在 1，这是正确的：
  它们的状态从构造那一刻起就没变过。
