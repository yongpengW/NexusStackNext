# 持久化业务任务归所属上下文，Scheduling 负责计划触发

NS 的 AsyncTask 把任务登记、后台执行、状态查询和人工重试组织在一起，PoS 在此基础上增加了
创建去重、执行代次、续期和任务关联。NSN 要保留这种调用体验，同时让每个业务上下文拥有自己的
数据与事务。用户于 2026-10-02 确认首轮切片与测试缝；实现由
[精简定价样板的持久化重算与恢复](https://github.com/yongpengW/NexusStackNext/issues/27) 跟踪。

## 职责与数据所有权

- **业务任务**表示所属上下文尚需完成的一项工作。任务意图与引起它的业务变更在所属数据库的
  同一事务内保存；工作进程只访问自己上下文的数据。
- **Outbox**保存需要可靠发布的集成事件。事件由发布方的 Contracts 显式声明名称与版本，
  接收方使用自己的 Inbox 与业务事务处理；它不承担通用业务任务的生命周期。
- **ScheduledTask**描述按计划到期的触发条件。Scheduling 可以发布 TaskDue，
  目标上下文接收后决定是否登记自己的业务任务，不接受任意程序集名或 CLR 方法名远程执行。
- 任务登记、领取和运行状态属于业务聚合的执行元数据，不因此增加一个要跨事务修改的业务聚合。
  一次业务提交只修改一个业务聚合及其执行元数据；其他聚合通过各自任务或事件继续处理。

这收窄了 CONTEXT-MAP 与 Scheduling 词表中“异步任务与计划任务的定义、触发与生命周期”
容易引发的集中归属解释。两处文档已同步收窄；不推翻 ADR-0013 的平台宿主安排，
也不改变 ADR-0004 的跨上下文契约约束。

## 第一条验证链路

以精简的定价样板验证“成本更新 → 持久化重算请求 → 后台计算 → 结果查询”。
样板使用自己的数据库和宿主，不由 PlatformHost 装配。公式明确标为演示规则，
不复制公司商品数据、费用规则、税费、汇率、SMT 或 MasterPricing 的完整业务实现。

第一轮只在该上下文实现业务任务。第二个真实消费者出现后，再决定哪些实现值得移到
BuildingBlocks；不会先建一个只有一个调用方的通用任务框架。

## 可靠性协议

1. 命令成功表示业务输入与任务意图都已提交。请求取消、异常或事务回滚不得留下只成功一半的状态。
   客户端提供稳定的请求标识，提交结果不确定时可以用同一标识重试或查询。
2. PostgreSQL 是任务事实来源。短事务原子领取任务，领取成功后结束该事务再执行耗时计算，
   不持有数据库行锁等待整个计算结束。
3. 每次领取获得新的执行代次与有限租约。失败回写、完成回写都验证当前持有者。
   租约过期后旧工作进程可能还在运行，不能仅凭本地取消令牌认为它已停止。
   首轮有限本地计算不续期；未来长任务若加入续期，也必须验证持有者。
4. 保存业务结果时，在同一数据库事务内校验任务执行代次、有效租约与业务输入版本，
   并提交业务结果和任务完成状态。失去执行权或输入已经更新的计算不得覆盖当前结果。
5. 领取与完成是两个事务，因此允许重新计算。任务协议保证可恢复，业务写入需要幂等；
   不承诺任意外部 HTTP、邮件或支付副作用恰好执行一次。
6. 同一请求标识且内容相同，返回已有任务；同一标识内容不同，返回冲突。
   不同请求是否合并由任务业务语义决定。重算可以只保留最新有效结果，通知、扣款等不能照搬。
7. 暂时失败有有界重试与可观察的等待状态，耗尽后进入失败终态；人工重试留下新的执行记录。
   重启后待处理任务仍可查询，过期执行可接管。

第一轮实现的精确范围与测试缝以确认后的 GitHub 规格和票据为准；本 ADR 不充当实施跟踪器。

## Redis 与消息总线的位置

Redis 用于有明确过期和故障策略的缓存及辅助协调。任务是否已登记、谁有权提交业务结果，
由业务数据库约束；Redis 清空或临时不可用不能把已接受的任务变成丢失的任务。

第一条同上下文链路可以从数据库发现任务。RabbitMQ 后续用于可靠跨上下文事件，
或作为减少轮询延迟的通知；若加入通知，丢失通知也必须能由数据库扫描恢复。
任务能力不会要求业务方同时正确编排“写业务、写任务、发 MQ、删 Redis”四个独立动作。

## Considered Options

- **所有任务存入 Scheduling 的库**：便于集中查看，但任务登记与其他上下文的业务提交无法成为
  本地原子事务，且很容易形成跨上下文查询。集中运维视图可以以后由契约构建，不接管数据所有权。
- **只有 RabbitMQ 消息**：缺少业务任务的可查询状态与重放依据，不能等同于 AsyncTask 的使用体验。
- **Redis 锁作为业务正确性的唯一依据**：锁丢失后旧执行仍可能写入，且数据库不会自动识别该锁。
  业务提交必须有数据库可以验证的执行权与版本条件。
- **立即抽取通用任务 SDK**：尚无第二个消费者证明接口，容易把定价重算的合并规则推广到所有任务。

## Consequences

各业务上下文承担自己的任务存储、迁移与运行配置。样板必须使这条路径容易复制，
但不会以共享业务 DbContext 或跨库事务换取表面上的少写代码。

单机先验证进程崩溃后的恢复与两个工作进程的正确性；主机整体故障下的可用性仍取决于未来部署，
不能由这条任务协议或一次测试通过推导出来。
