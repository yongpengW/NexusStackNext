# 平台能力合并为一个宿主与一个数据库

## 背景：用户提出了一个我答不上来的质疑

最初的 ADR-0001 把系统切成五个限界上下文，ADR-0002 让**每一个独占一个数据库**。
用户质疑：

> Identity / Platform / Scheduling / Auditing / Files 更像是一个大型系统的**基础服务**，
> 属于设计好后基本不会变化的基础设施，落到**一个基础设施数据库**明显更符合常理。
> 后续扩展的不同**业务模型**按照具体业务场景来设计独立上下文数据库可能是合理的，
> 但目前这个设计我不能认同。

**这个质疑是对的**，而且它指向的不只是数据库。

## 我犯的推理错误

DDD 本来就把子域分成三类：

| | 是什么 | 该怎么对待 |
|---|---|---|
| **核心域** | 业务差异化所在 | 精雕细琢 |
| **支撑子域** | 必要、自建，但不是差异化 | 适度自建 |
| **通用子域** | 已解决的问题 | **优先买/用现成的** |

这五个全部是通用或支撑子域——它们不是差异化所在，而且都有成熟替代品
（Keycloak、S3/MinIO、Quartz、Seq）。**DDD 对这三类的建议本来就不同，
而我把同一条规则均匀地套在了五个性质相同、且都不是核心域的东西上。**

更根本的是，我把**三件事当成了一件**：

- **限界上下文** —— 建模边界
- **可部署单元** —— 运维边界
- **数据库** —— 数据边界

DDD 从没说这三者要 1:1:1。我从"5 个限界上下文"直接推到"5 个服务 × 5 个库"，
**中间那一步没有论证过**。

## 决定

五个平台能力**合成一个可部署单元与一个数据库**：

```
src/Services/<Ctx>/{Domain,Application,Infrastructure}   ← 五个模块，程序集边界不变
src/Services/<Ctx>/NexusStackNext.<Ctx>.Endpoints/       ← 模块的 HTTP 面（Add*Module / Map*Endpoints）
src/Hosts/NexusStackNext.PlatformHost/                   ← 唯一宿主，显式组装五个模块
数据库：nexusstack_platform，库内按 schema 分开（identity / platform / scheduling / auditing / files）
```

**未来的业务上下文仍然各自独立成服务、独立库**——那才是需要按业务边界切分的地方。

一句话：**平台是模块化单体，业务是微服务。**

## 为什么不能只合并数据库、保留五个服务

那是**分布式单体**：分布式部署的全部复杂度（网络、序列化、部分失败、可观测性）
配上共享数据的全部耦合——两边的好处都没拿到。

**共享一个数据库的前提是共享一个进程。** 二者必须一起选。

## 什么**没有**变

这一条很重要，因为它决定了这次改动的风险面：

- 五个上下文的 `Domain` / `Application` / `Infrastructure` 程序集照旧独立
- **跨上下文引用仍然为零**
- 架构不变量测试**一条没改**（不变量 1、2、3 全部照旧守着）
- 网关的路由与授权策略**逐条不变**——`requireAuthentication` 一个都没动
- 所有路由前缀不变，因此合并**不需要改任何端点路径**

变的只有"跑在几个进程里"和"连几个库"。

## 一个顺带消失的配置风险

五个进程时，每个都要一个**不同的** Snowflake `WorkerId`——配重了会产生重复 ID，
**不报错，只在数据里留下两条同 ID 的记录**。现在只有一个进程，只需要一个 WorkerId。

## Considered Options

- **维持 5 服务 × 5 库**：正统，但把通用子域当核心域对待，运维成本换不到边界收益。
- **5 服务 × 1 库**：分布式单体，见上，不自洽。
- **1 服务 × 1 库（本决定）**：与"这些能力一起演进、一起部署"的事实一致。

## Consequences

- 失去按能力独立扩展的能力。**这一条对 Auditing 是真实代价**：它是 append-only、
  高写入量、带保留期策略的负载，与 Identity/Platform 的读写特征不同。
  它若真的成为瓶颈，应当**独立出去**——那时它有独立的库与独立的服务，而不是共享平台库。
- 五个模块共用一个库，schema 之间 join 在技术上可得。**边界靠 schema + 迁移历史隔离，
  不靠连接串隔离**——比五库弱一档，这是这个决定主动接受的代价。
- 模板少了一个"5 个独立服务"的演示样本。那是教学价值，不是工程价值。

## 实测

合并过程中真的踩到一个只有合并才会暴露的问题：

```
System.ArgumentException: An item with the same key has already been added. Key: T:Program
```

五个模块各自还留着 `Program.cs`（顶层语句生成的全局 `Program` 类），
加上宿主一共六个同名类型，**OpenAPI 文档生成 500**。
删掉模块的入口点（它们本来就不该有）后恢复 200，文档里 20 条路径。

**这正是"一次只改一件事、每步都验证"的价值**：如果不做运行时验证，
这个 500 会留到用户第一次打开 `/openapi/v1.json` 时才被发现。
