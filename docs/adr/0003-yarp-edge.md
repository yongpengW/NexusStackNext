# YARP 作为独立边缘服务：认证在网关，授权在上下文

原项目的网关引用了包含全部业务与基础设施的 `NexusStack.Core`，路由依赖手工维护的 proxy 配置，
且路由管理 API（`GET/POST/PUT/DELETE /routes`）没有任何鉴权。

决定：`src/Gateway/` 保留 YARP 作为独立边缘服务，负责路由、**认证（验签）**、限流、关联 ID、汇聚 Swagger。
**授权（这个用户能不能做这件事）留在各上下文**。网关不得引用任何上下文的 `Domain` 或 `Infrastructure`。

## Considered Options

- **不要网关 / 只用 Aspire 开发期网关**：前端直连各服务，鉴权与限流会散到每个服务，版本收敛也无处安放。
- **把授权也放网关**：每新增一个上下文都要改网关，且网关必须理解各上下文的权限模型——耦合方向反了。

## Consequences

- 路由配置必须持久化并支持热更新；原项目 `JsonProxyConfigStore` 的并发处理值得沿用。
- 网关的路由管理 API 必须鉴权——这一条原项目缺失，是重做时必须补上的。

## 故障处理与配置发布（2026-10-01）

目标摘除使用 YARP 的主动健康检查。默认探测 `/health/ready`，间隔 5 秒、超时 2 秒，
连续失败 2 次后停止转发，首次成功后恢复。集群的 `healthCheck` 可以调整这些参数；
显式 `null` 仅用于没有就绪端点的外部服务。后端就绪检查不得反向依赖网关。
可用目标策略为 `HealthyAndUnknown`：初始未知节点可以接流量，全部节点已被判定不健康后返回 503，
不使用默认的 `HealthyOrPanic` 回退。故障被发现之前仍可能返回 502/504；不自动重试业务请求。

`/health/live` 只反映网关进程存活；`/health/ready` 独立探测每个集群，至少一个目标就绪才算该集群可用。
它和状态广播共用探针，使用相同的就绪路径；显式关闭主动检查的集群退回 `/health/live`。
当前 readiness 要求所有集群可用。未来增加独立业务服务后，须重新决定哪些集群是边缘就绪的必要依赖，
避免一个可降级服务故障导致整个边缘被编排系统移除。

`gateway.default` 是每个网关进程内、按路由标识与调用方分区的固定窗口限流，默认每分钟 100 次、无等待队列。
认证先于限流：有有效 `sub` 的身份使用验签后的 `iss + sub`，匿名或缺少 `sub` 使用连接 IP。
原始 URL 和客户端提交的 `X-Forwarded-For` 不作为分区键。429 附带 `Retry-After`，Files 路由同样启用。
部署在可信反向代理后面时，应另行配置可信代理边界；当前直接使用连接 IP，NAT 后的匿名用户会共用额度。

路由管理在一个写锁内完成“读取最新快照 → 修改 → NSN/YARP 校验 → 保存 → 发布”。
标识唯一性与 YARP 一致，不区分大小写。启动与热更新共用限流策略白名单。
此外通过宿主的参数策略工厂解析路径约束；YARP 仅检查路径语法，无法单独挡住未知约束或错误约束参数。
不同路由的并发修改不会丢失；同一路由仍是按执行顺序覆盖，不提供 ETag 或编辑冲突检测。
无效配置返回 400，重复标识 409，缺失路由 404，存储写入失败 503；失败时不发布候选配置。

204 表示配置已持久化并发布给 YARP。YARP 异步应用完整快照，正在执行的请求继续使用旧配置；
不承诺 204 返回瞬间所有请求已切换。管理查询、健康探针和文档聚合使用同一份进程已接受的快照，
文档缓存随配置变化失效。直接编辑磁盘需要重启，不会被查询接口冒充成热更新。

文件存储只允许一个网关进程作为写者。每实例限流也不会跨副本共享额度。
这些行为提高单实例正确性和有副本的下游集群容错能力，不能消除单机/单网关故障点。
真正的多机高可用还需要部署拓扑、共享配置控制面、配额策略及数据层恢复方案。

验证通过真实 Kestrel 网关与可控 HTTP 后端进行，包括故障摘除/恢复、调用方与路由隔离、
并发 CRUD 的实际转发、非法配置拒绝、存储故障及重启恢复；查询接口的 200 不替代转发验证。
