# 配置中心的应用划分：一个基座 + 每个宿主一个应用

## 决定

AgileConfig 里建 **3 个应用**：一个基座 + 两个宿主应用，宿主应用**关联（继承）**基座。

```
nexusstack_shared          ← 基座
  ├─ nexusstack_gateway      边缘
  └─ nexusstack_platform     平台宿主（五个平台能力在同一个进程里）
```

沿用参照仓库已验证的继承模式（旧版是 3 个应用，MQ 与 PlanTask 关联 API）。
应用数仍是 3——因为**可部署单元仍是"边缘 + 一个应用"**（平台能力已合并为一个宿主，见 ADR-0013）。

## 两条硬规则

### 基座里**绝不放** `ConnectionStrings`

ADR-0002：**每个上下文独占一个 PostgreSQL 数据库**。把连接串放进基座，
平台宿主就会继承到同一个库——等于在配置层把"上下文拥有自己的数据"（不变量 1）抹掉：
谁都能连进去 join 别人的表，而**没有任何代码或测试会反对**。

连接串必须逐上下文一份，且**库名不同**。

### 基座里**绝不放** `WorkerId`

雪花算法的 WorkerId 必须**每进程唯一**。多个进程共用一个 WorkerId
会**产生重复 ID**——不会立刻报错，只在数据里留下两条同 ID 的记录。

参照仓库的配置中心里 `WorkerId=1` 是共享的。本仓**每个宿主各自一个**，值写在宿主的 `Program.cs` 里
（不放进基座配置——理由就是上面那句）。

> **2026 年第 26 轮 review 更正了一处已经过时的说法。** 这里原写"本仓现在是 101–105，逐个宿主不同"，
> 那是**五个宿主**时代的数字。ADR-0013 把五个平台能力合成**一个宿主**之后，
> 全仓只有一个 `WorkerId`（`101`，在 `PlatformHost/Program.cs`）——
> **这一点 ADR-0013 自己也写着**（"现在只有一个进程，只需要一个 WorkerId"），
> 于是两条 ADR 互相矛盾了一阵子。**规则不变，数字更新。**

## 为什么不用"全部共用一个应用"

最省事，但每个服务都能读到其它服务的数据库口令——
与"上下文拥有自己的数据"直接冲突，而配置中心是这种冲突最容易发生的地方：
它看着只是几条配置项，实际是在分发凭据。

## 为什么不用"每个能力一个自包含应用、不继承"

没有隐式继承，每个服务的配置一目了然。代价是 RabbitMQ / Redis / Serilog
在每个能力各自的应用里各一份——**broker 换地址要改多处**，而漏改一处不会有任何提示。

继承的代价是"看一个应用看不全它的配置"。这个代价换来的是一处维护，值。

## 已知的行为：数组不合并

AgileConfig 的继承是**按配置项**合并的，**数组会整体替换**，不是逐元素追加。

后果：宿主应用里一旦写了 `Serilog:WriteTo`，基座里的同名数组就**整个失效**。
这大概率不是你要的（会丢掉 Console sink，而"一行日志都没有"正是最难排查的处境）。

因此 `config/*.template.json` 里每个宿主应用都**重复了 Console sink**。
加 sink 时请照做。

## Considered Options

- **纯 appsettings + 环境变量**：ADR-0006 已否决（失去热更新与集中管理）。
- **每个宿主一个应用、互不继承**：见上。
- **全部共用一个应用**：见上。

## Consequences

- 新建一个上下文时，要同时建一个 AgileConfig 应用并关联基座——两步，漏一步就是"配置不生效"。
- 基座与宿主应用的职责边界靠**约定**维持，没有任何东西强制它。
  唯一的自动化守卫是 `scripts/assert-no-credentials.ps1`：连接串口令一旦落进仓库就会被拦下。
- 优先级（环境变量 > AgileConfig > `appsettings.{Env}.json` > `appsettings.json`）
  有测试守着，见 `tests/Composition.Tests/ConfigurationPriorityTests.cs`。
