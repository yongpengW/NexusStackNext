# 第一个根账号由配置播种，而不是靠一次性 CLI 或"首个注册者"

`AccessPolicy` 里有一条 `IsRoot` 旁路，用于"系统还没有任何授权数据"的引导期；而它此前**不可达**：
`User.Register` 的 `isBuiltIn` 参数永远是 `false`，没有任何账号能走上去。
于是权限链断在第一环——建不出菜单 ⇒ api-resource 挂不上 ⇒ 角色授不到权限 ⇒
所有受权限保护的端点永远 403，而所有测试都是绿的（票据 67）。

决定：**宿主启动时读 `Identity:Root:UserName` / `Identity:Root:Password`，幂等地播种一个内置根账号**
——存在同名账号就跳过，**绝不重置口令**。配套的一半是**菜单由 HTTP 端点管理**（只对根账号开放），
因为"有一条链"与"链能被建起来"是两件事：前者是判定逻辑，后者是它的入口。

## Considered Options

- **一次性 CLI（`create-root`）**：不进启动路径，生产更干净。代价是多一条**必须被记住**的命令，
  而忘记执行的后果是"新环境没有任何人能授权"——一个只有运维手册知道、代码里看不出来的状态。
- **首个注册者即根**：零配置。代价是把"谁先注册谁说了算"变成一个**竞态**，
  而它恰好发生在暴露到公网的第一秒。这不是"概率低"，是"在正确的时机攻击必然成功"。
- **启动时按配置播种**（本决定）：模板开箱可用，与既有的"必需配置"形状一致
  （宿主读不到必需配置时明确失败，而不是静默降级）。代价写在下面。

## Consequences

**必须写进部署文档的一条**：配置里存在一个**能进一切的账号**。`IsRoot` 旁路不对它做权限判定，
所以上线后第一件事是**轮换它的口令**，不需要它的环境里干脆不要配这两个键。

**口令以明文形式住在配置里**（播种时当场哈希）。这不是疏忽：本仓的口令哈希是 Pbkdf2 带**随机盐**，
人手算不出可复现的值；而它本来就和其它凭据一样住在被 gitignore 的 `env/*.dev` 或配置中心里。
换句话说，"放哈希"并不比"放口令"更安全——哈希本身也是能登录的凭据。

**`IsRoot` 的可达性依赖令牌里带 `Root` 声明。** 这条旁路此前"有测试但不可达"，一半原因是没有根账号，
另一半原因是**签发器从不写那个声明**（令牌里只有 sub / name / jti / 会话版本）。
两处必须同时成立，缺一处则旁路仍然不可达——而它们的失效方式都是**没有任何报错**。
这一条是"种一个根账号"这件事单独做也没用的原因，也是它值得记在这里的原因。

**配置缺失与配置非法是两件事**：没配 `Identity:Root:*` 是合法的（很多部署不需要根账号），
记一条 Information 就够；而配了却建不出来（用户名非法、口令哈希失败）是**配置事故**，
必须让宿主起不来——否则它会以"启动成功、但没有人能授权"的形态活着。

**菜单管理端点只对根账号开放**，因为菜单管理的权限键还没有登记。
它留了一条正规的升级路径：登记一条 `/api/identity/menus` + `POST` 的 api-resource 并授予某个角色，
即可把菜单管理交出去，**不必改代码**。

**这条决定的是"引导期"，不是"日常"**：链一旦建起来（有人能授权、角色能授到菜单），
根账号的日常用途应当降到零。它的存在是为了让系统从零启动，而不是为了长期使用。
