# Outbox 失败只修改读取时的恢复版本

两个投递器可能读取同一条待投递消息。其中一个使消息停止后，管理员恢复了消息，而另一个投递器
仍在等待 broker。后者迟到的失败过去只按消息 ID 更新，会扣掉新预算，甚至把刚恢复的消息再次停止。
这个问题同时存在于来源操作日志、Platform 审计消息、Scheduling 发生消息及 Costing 结果交付。

## Decision

`OutboxEntry.RetryRevision` 从零开始，每次受控恢复成功增加一；自动失败、停止及成功确认不改变它。
恢复仍保留消息身份、载荷及原发生时间。恢复版本属于来源投递状态，不进入事件载荷或封套，
不改变中央内容指纹或消费者去重身份。到达最大版本时拒绝继续恢复，不能溢出后重新命中旧请求。

投递器保存读取到的恢复版本，汇报失败和死信时必须携带它。`IOutboxStore` 的实现同时校验当前仍为
Pending 且版本匹配；校验和更新在同一个行锁事务或内存临界区内执行，不能先查询再无条件写入。
不匹配时保持原状态，并返回 false；投递器只把实际写入的变化计入重试/死信数。
因此忽略旧失败后，日志不会错误声称新一轮消息已经停止或消耗了预算。

成功确认不要求版本匹配。恢复前后是同一消息和同一内容，旧一轮获得的真实 broker 确认仍证明 broker
已接管消息，应阻止不必要的重投。重复确认保留首次成功时间，后续失败不能覆盖已确认结论。
这仍是至少一次发布与消费幂等，不是恰好一次发送，也不是同时只允许一个发布者的租约。

## Consequences

公共 Outbox 端口的两个失败方法要求恢复版本，并返回是否生效；所有实现及调用点一起迁移。
Platform、Scheduling 和日志恢复统一使用 `RetryDelivery`，Costing 原先自行清零预算的路径也改用它。
每个拥有 Outbox 的上下文自行增加其列和迁移，不引入跨上下文 JOIN。
升级须停旧发布者与旧恢复写入者，执行对应迁移再统一启用新版本；旧二进制不遵守版本条件，不能混跑。

单轮投递中多个发布者的重复发送仍由消费者去重处理；该版本不充当任务执行租约，也不为旧的业务管理
HTTP 接口自动增加恢复请求版本校验。操作日志管理端口已有时间加版本条件，其余管理契约逐项验收。

`OperationJournalDeliveryTests` 在 Memory / PostgreSQL 的公共投递器、存储维护端口和可阻断 broker 缝验证：
读消息后暂停发布、另一发布者停止、管理员恢复，再释放旧失败或真实确认；还检查新一轮真实失败仍可生效，
以及被忽略失败不计入重试或死信。Costing 的公开命令/查询旅程验证独立实现同样遵守恢复版本。

## Considered Options

- 管理前要求人工等所有发布者退出：把正确性责任交给操作顺序，无法识别迟到结果。
- 仅比较停止时间或尝试次数：恢复会清零尝试次数，同一时间也可能再次停止，旧状态可能误命中新一轮。
- 日志模块维护单独的版本字段：业务消息仍有相同缺陷，多个恢复实现会逐渐分叉。
- 拒绝旧版本的成功确认：消息身份和内容没有变化，会无故丢掉真实发布确认并造成额外重投。
