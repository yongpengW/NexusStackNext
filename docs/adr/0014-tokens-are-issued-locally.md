# 令牌由本上下文签发，验签交给框架

## 背景：一个被搁置了很久的决定

票据 10 从写下那天起就卡在这里。它的开头是这样一句：

> 原项目是**自研 JWT + 自建 Token 表**；但你的 git 里有一个 `dev-authentik` 分支，
> 说明考虑过接外部 IdP。**先定形态再动工**。

三个选项摆在桌上：自研、OpenIddict、外部 IdP。没有一个明显更对，所以这条票据
一直停在 `needs-info`，而它的另一半（登录、锁定、不泄露用户存在性）也陪着一起停着
——尽管那一半**与形态毫无关系**。

**先做无关联的那一半**，是这一轮实际发生的事。等登录防护带着 7 条测试落了地，
这个决定从"开工前的门槛"变成了"最后三分之一的岔路口"——**同一个决定，在不同的时刻问，
代价完全不同。**

## 决定

**A：令牌由 Identity 上下文自己签发，验签用框架自带的 JWT Bearer 处理器。**

## 为什么

### 一、领域层已经为它建好了

这不是"三个选项里我挑了一个"，而是**其中两个会让已有的东西作废**：

| 已经存在的 | 位置 |
|---|---|
| `RefreshToken` 聚合（签发、撤销、`unusable` 原因） | `Identity.Domain/Tokens` |
| `RefreshTokenIssued` / `RefreshTokenRevoked` 领域事件 | `Identity.Domain/Events` |
| `identity.refresh_token.unusable` 错误码 | `IdentityErrors` |
| `refresh_tokens` 表与 `ux_refresh_tokens_hash` 唯一索引 | 迁移 `InitialIdentity` |

选 **B（OpenIddict）** 会得到**两套并行的令牌模型**——它自己的 `OpenIddictTokens` 表，
和我们这套聚合。两套模型意味着两条真相，而它们迟早会不一致。
选 **C（外部 IdP）** 更彻底：用户主数据不在自己库里，
而 `users` / `roles` / `menu_trees` / `menu_nodes` / `api_resources` 这套
RBAC 模型的前提正是"用户在这里"。

**A 是唯一一个不与既有结构打架的选项。** 当三个方案在纸面上势均力敌时，
"哪一个不需要拆掉已经建成的东西"往往就是那个决定性的依据——而它只有在
**认真看过自己已经建了什么**之后才看得见。

### 二、"自研 JWT"这个说法容易读错

它不意味着手写 HMAC 或 RSA。签名与验证仍由 **`Microsoft.AspNetCore.Authentication.JwtBearer`**
完成——那是 .NET 平台自己的包，不是第三方依赖。

**我们负责的是生命周期**：签发什么、活多久、怎么轮换、怎么撤销、多端怎么共存。
那恰恰是参照仓库出错的地方（明文存储、可重放、撤销不生效），
也恰恰是没有哪个库能替你决定的部分。

### 三、边缘早就等着它了

ADR-0003 的网关已经有一套认证缝，而它当前是个**显式拒绝**的实现，
选 A 之后网关验签与后端签发用的是同一套密钥与同一种令牌，
**不需要在边缘再引入一个 OIDC 客户端**。

> **第 26 轮 review 更正了这句的后半段。** 这里原写"`/gateway/openapi/sources` 与边缘的
> Swagger UI **至今未受保护**"，把它当成一个待修的缺陷。**位置后来变了**：
> 边缘的 `/swagger` 是"**总是开**"的**有意设计**——它就长在边缘上，那正是要暴露的地方
> （见 `AGENTS.md` 的端点清单）；而平台宿主的 `/swagger` 才是"仅 Development"，
> 因为它会**绕过边缘**暴露全部 API 面。
>
> **`/gateway/openapi/sources` 仍然未受保护**，这一半仍然属实——它泄漏的是
> "聚合器从哪些来源取到了文档、各多少条路径"，属于运维信息，是否要收口是另一件事。

## 后果

**会发生的：**

- Identity 上下文新增令牌签发用例与 `refresh_tokens` 的写入路径
  （表与索引已在迁移里，不需要新的迁移）。
- 网关换成真正的 JWT 验签；未认证请求从"显式拒绝"变为"验签失败"。
- 票据 11 的版本号失效机制要为令牌撤销留一个入口（验收 5：撤销后旧 access token 立即失效）。

**要接受的代价：**

- **轮换、重放检测、多端撤销都要自己写对。** 没有库替你兜底。
  这是选 A 的**主要风险**，也是票据 10 剩下的验收里最需要测试的部分——
  每一条都要有能失败的反向验证。
- 密钥管理成为我们的责任（`env/` 与 AgileConfig 的边界要写清楚）。

**明确不做的：**

- 不引入 OpenIddict，即使将来要接第三方登录——那时它是一个**新的**授权服务器，
  而不是替换掉自己的令牌模型。
- 不做 OIDC 发现端点与 JWKS。当前没有第三方消费方；
  等出现第二个消费方（那正是本仓"两个才是真的缝"的那条判据）再加。
